Style Dictionary로 토큰을 CSS로 빌드하기

packages/tokens/scripts/build-tokens.ts의 buildTokens는 토큰 JSON을 읽어 CSS 텍스트를 돌려주는 함수다. Primitive는 실제 값으로, Semantic은 Color Scheme(light/dark) 블록마다 var() 참조로 낸다. 이 함수가 Style Dictionary에 넘기는 옵션을 하나씩 뜯어 보고, 옵션을 바꾸면 출력이 어떻게 달라지는지 직접 실행한 결과로 보여 준다.

한눈에 보기

파란 줄은 buildTokens 안에서 일어나는 일이다. Style Dictionary를 세 번 실행해 나온 CSS 블록을 이어 붙인다. 파일을 읽고 문자열을 돌려줄 뿐 파일을 기록하지 않는다. 초록 줄은 pnpm build가 이 함수를 실제 토큰 폴더로 불러 결과를 파일로 기록하고, tsdown이 dist/를 채우는 흐름이다.

buildTokens(토큰 폴더)
  1. primitive.json을 읽는다
  2. 1번째 실행: Primitive → 헤더 + :root 블록
  3. 2번째 실행: Primitive + light → light 블록
  4. 3번째 실행: Primitive + dark → dark 블록 2개
  5. 블록 4개를 이어 { css }로 돌려준다
pnpm build
  1. build.ts: buildTokens("tokens/")
  2. build.ts: generated/tokens.css에 기록한다
  3. tsdown: dist/를 비우고 dist/index.js를 만든다
  4. tsdown: generated/tokens.css를 dist/로 복사한다

파일 기록을 함수 밖(build.ts)으로 뺀 이유는 테스트다. 테스트는 fixture 폴더로 buildTokens를 부르고 돌려받은 문자열만 검사한다. 디스크에 아무것도 남기지 않는다.

Style Dictionary가 하는 일

Style Dictionary는 플랫폼 중립의 토큰 JSON 하나를 플랫폼마다 다른 모양(CSS 변수, iOS Swift 상수, Android XML 등)으로 바꾸는 빌드 도구다. 바꾸는 일은 아래 순서로 나뉘고, 설정의 옵션은 각 단계에 무엇을 할지 알려 준다.

  1. 토큰 읽기 tokens(객체)나 source(파일 경로)로 받은 JSON을 합친다. $value가 보이면 DTCG 형식으로 판단한다. 우리 설정에서 sd.usesDtcg는 true였다.
  2. 플랫폼 고르기 platforms의 키 하나(우리는 css)를 골라 그 플랫폼의 설정으로 아래 단계를 돈다.
  3. transform 토큰마다 이름(name), 값(value), 속성(attribute)을 바꾼다. 예를 들어 색 객체를 #18181b로, 경로 color.gray.900을 gyeol-color-gray-900으로 바꾼다.
  4. 참조 해석 {color.gray.900} 같은 참조를 찾아 가리키는 토큰과 잇는다. Primitive에는 참조가 없고, Semantic은 모든 값이 참조다. outputReferences를 켜면 값으로 풀지 않고 var()로 남긴다(참조가 var()가 되기까지).
  5. format transform이 끝난 토큰 목록을 파일 내용(문자열) 하나로 만든다. css/variables는 :root { --이름: 값; }을 만든다.
  6. 기록 문자열을 buildPath + destination 파일로 기록한다. buildTokens는 이 단계를 부르지 않는다.

스크립트를 위에서부터

build-tokens.ts는 아래 순서로 읽으면 된다. 함수가 여럿이지만 하는 일은 "Style Dictionary를 세 번 돌려 나온 CSS를 이어 붙인다" 하나다.

1. Color Scheme과 블록의 selector

const COLOR_SCHEMES = ["light", "dark"] as const;

type ColorScheme = (typeof COLOR_SCHEMES)[number];

/** 바깥에서 안쪽 순서로 중첩하는 selector 목록. 예: `["@media …", ":root"]` */
type SelectorChain = readonly string[];

const SCHEME_SELECTORS: Record<ColorScheme, readonly SelectorChain[]> = {
  light: [[":root"]],
  dark: [
    [
      "@media (prefers-color-scheme: dark)",
      ':root:not([data-color-scheme="light"])',
    ],
    [':root[data-color-scheme="dark"]'],
  ],
};
  • COLOR_SCHEMES는 빌드할 Color Scheme의 목록이자 CSS에 내는 순서다. ColorScheme 타입("light" | "dark")도 이 배열에서 끌어내서, 목록을 한 곳에만 적는다.
  • SCHEME_SELECTORS는 Color Scheme마다 만들 CSS 블록의 selector다. light는 블록 1개, dark는 블록 2개(OS 설정, 속성)다. ["@media …", ":root:not(…)"]처럼 배열이면 앞의 것이 바깥, 뒤의 것이 안쪽인 중첩 블록이 된다. 왜 이 selector인지는 Color Scheme 블록에서 경우를 모두 펼쳐 보인다.

2. 토큰 파일을 직접 읽고, 세 번 빌드해 이어 붙인다

export async function buildTokens(tokensDir: string): Promise<BuildResult> {
  // 파일 경로를 Style Dictionary의 source 옵션으로 넘기지 않고 직접 읽는다.
  // source의 항목은 경로 하나라도 glob 패턴으로 풀리고, 맞는 파일이 0개여도 오류가 아니다.
  // 그러면 토큰 없이 빌드가 끝나 빈 ":root {}"가 나온다. 직접 읽으면 파일이 없을 때 ENOENT로 실패한다.
  const primitive = await readJson(join(tokensDir, "primitive.json"));

  const cssBlocks = [await buildPrimitiveCss(primitive)];
  for (const colorScheme of COLOR_SCHEMES) {
    const semantic = await readJson(
      join(tokensDir, "semantic", `${colorScheme}.json`),
    );
    cssBlocks.push(
      ...(await buildSemanticCss(primitive, semantic, colorScheme)),
    );
  }
  return { css: cssBlocks.join("\n").trimEnd() + "\n" };
}

이 함수가 전체 흐름이다. 칠한 줄을 차례로 읽으면 이렇다.

  1. Primitive를 읽는다 primitive.json을 직접 읽는다. 왜 Style Dictionary에 경로를 넘기지 않는지는 tokens와 source에 있다.
  2. Primitive 블록을 만든다 buildPrimitiveCss가 맨 위 헤더와 :root { --gyeol-color-…: #…; }를 만든다.
  3. Color Scheme마다 Semantic 블록을 만든다 light, dark 순서로 semantic/light.json, semantic/dark.json을 읽어 buildSemanticCss에 넘긴다. light는 블록 1개, dark는 블록 2개를 돌려준다.
  4. 이어 붙인다 블록 4개를 빈 줄 하나씩 두고 이어 붙여 CSS 텍스트 하나로 돌려준다.

3. Primitive: 지난 티켓과 같은 설정

const cssPlatform = (files: File[]): PlatformConfig => ({
  prefix: PREFIX,
  transformGroup: "css",
  files,
});

async function buildPrimitiveCss(primitive: DesignTokens): Promise<string> {
  const sd = new StyleDictionary({
    tokens: primitive,
    log: { verbosity: "silent" },
    platforms: {
      css: cssPlatform([
        { destination: "tokens.css", format: "css/variables" },
      ]),
    },
  });
  return (await formatOutputs(sd)).join("");
}

Primitive와 Semantic 빌드가 함께 쓰는 플랫폼 설정(prefix, transformGroup)은 cssPlatform으로 뺐다. Primitive 빌드는 기본 format css/variables를 그대로 써서, 파일 맨 위 헤더(Do not edit directly…)와 :root 블록을 만든다. 각 옵션이 하는 일은 아래 표와 같다.

옵션 값 하는 일
tokens 읽은 객체 빌드할 토큰 트리 tokens와 source
log.verbosity "silent" Style Dictionary의 콘솔 출력을 끈다 log.verbosity
platforms.css 설정 객체 "css"라는 이름의 출력 하나. 이름은 우리가 정한다 platforms와 prefix
prefix "gyeol" 변수 이름 앞에 붙일 말
transformGroup "css" CSS용으로 미리 묶어 둔 transform 14개를 쓴다 transformGroup과 transforms
files[].destination "tokens.css" Style Dictionary가 파일을 기록할 경로 formatPlatform은 파일을 기록하지 않아서 돌려받는 값에 이름표로만 붙는다. 실제 기록은 build.ts가 한다
files[].format "css/variables" 토큰 목록을 :root { … } 문자열로 만든다 files: format과 options

4. Semantic: Primitive를 함께 넘기고 Semantic만 낸다

async function buildSemanticCss(
  primitive: DesignTokens,
  semantic: DesignTokens,
  colorScheme: ColorScheme,
): Promise<string[]> {
  const formats = SCHEME_SELECTORS[colorScheme].map((selectors, index) => ({
    name: `gyeol/css/${colorScheme}-${index}`,
    format: colorSchemeFormat(colorScheme, selectors),
  }));

  // Semantic에는 범주 그룹이 없어 최상위 이름이 Primitive 범주(color, spacing, radius)와 겹치지 않는다
  const sd = new StyleDictionary({
    tokens: { ...primitive, ...semantic },
    log: { verbosity: "silent" },
    hooks: {
      formats: Object.fromEntries(formats.map((f) => [f.name, f.format])),
    },
    platforms: {
      css: cssPlatform(
        formats.map(({ name }) => ({
          destination: `${name}.css`,
          format: name,
          filter: (token: TransformedToken) => hasTokenAt(semantic, token.path),
        })),
      ),
    },
  });
  return formatOutputs(sd);
}

Primitive 빌드와 다른 곳은 세 군데다.

다른 곳 코드 이유
토큰 { ...primitive, ...semantic } Semantic은 {color.white}처럼 Primitive를 가리킨다. 가리키는 대상이 함께 있어야 참조가 풀린다 참조가 var()가 되기까지
filter hasTokenAt(semantic, token.path) 함께 넘긴 Primitive가 Semantic 블록에 다시 나오지 않게, Semantic 파일에 있는 토큰만 낸다 Primitive는 참조 대상으로만
format colorSchemeFormat(…)을 hooks.formats에 이름 붙여 등록 블록마다 color-scheme 속성을 넣고 헤더를 빼야 해서 직접 만든 format을 쓴다 직접 만든 format

dark는 SCHEME_SELECTORS.dark에 selector가 두 개라 files도 두 개가 된다. 한 번 실행으로 내용이 같은 블록 두 개(media query 블록, 속성 블록)를 받는다.

5. 문자열만 받아 돌려준다

const formatOutputs = async (sd: StyleDictionary): Promise<string[]> => {
  const files = await sd.formatPlatform("css");
  return files.map(({ output }) => {
    if (typeof output !== "string") {
      throw new Error("Style Dictionary가 CSS를 만들지 못했다");
    }
    return output;
  });
};

formatPlatform은 files의 항목마다 { output, destination }을 담은 배열을 돌려준다. dark처럼 파일이 둘이면 항목도 둘이다. output의 타입은 문자열이 아닐 수도 있게 넓게 선언되어 있어서, 문자열인지 확인한 뒤 돌려준다. 자세한 내용은 formatPlatform에 있다.

토큰 하나가 CSS 한 줄이 되기까지

primitive.json의 토큰 하나는 이름과 값이 따로 바뀐 뒤 --이름: 값; 한 줄로 합쳐진다. 아래 값은 getPlatformTokens("css")로 transform이 끝난 토큰을 꺼내 확인한 것이다.

이름 ["color", "gray", "900"]경로 name/kebab + prefix gyeol-color-gray-900
색 값 { srgb, [0.0941, 0.0941, 0.1059] }DTCG 색 객체 color/css #18181b
alpha 있는 색 { srgb, [0, 0, 0], alpha: 0.5 } color/css rgba(0, 0, 0, 0.5)
dimension { value: 16, unit: "px" }DTCG dimension 객체 size/rem 16px 적힌 unit을 그대로 붙인다
합치기 이름 + 값 css/variables --gyeol-color-gray-900: #18181b;

완성된 변수 이름을 부분으로 나누면 이렇다.

--gyeol-color-gray-900 --는 css/variables format이 붙이고, 나머지는 name/kebab transform이 prefix와 경로를 -로 이어 만든다.

transform이 빠지면 Style Dictionary는 객체를 그대로 문자열로 바꿔 [object Object]를 낸다. 오류가 나지 않으니 출력을 봐야 안다. 설정을 바꾸면 나오는 CSS의 C 줄이 그 경우다.

참조가 var()가 되기까지

Semantic 토큰의 값은 실제 색이 아니라 다른 토큰을 가리키는 참조다. semantic/light.json의 bg-surface는 "{color.white}"이고, ring-offset은 다른 Semantic인 "{bg-surface}"다. 이 참조를 CSS에서도 참조(var())로 남기는 것이 Semantic 빌드의 핵심이다.

이름 ["bg-surface"]경로 name/kebab + prefix gyeol-bg-surface
Primitive 참조 "{color.white}" outputReferences var(--gyeol-color-white)
Semantic 참조 "{bg-surface}" outputReferences var(--gyeol-bg-surface) Semantic → Semantic도 같다
합치기 이름 + 값 colorSchemeFormat --gyeol-bg-surface: var(--gyeol-color-white);

outputReferences를 켜지 않으면 Style Dictionary는 참조를 끝까지 풀어 실제 값을 낸다. fixture의 light로 두 경우를 실행한 결과다.

참조로 내기outputReferences: true
bg-surface
var(--gyeol-color-white)
ring-offset
var(--gyeol-bg-surface)

bg-surface를 바꾸면 ring-offset도 따라 바뀐다. Figma에서 Semantic이 다른 Semantic을 가리키던 구조가 CSS에도 남는다. 우리가 고른 방법이다.

값으로 풀기outputReferences: false
bg-surface
#ffffff
ring-offset
#ffffff

지금 보이는 색은 같지만 두 변수의 연결이 끊긴다. 누군가 --gyeol-bg-surface만 바꾸면 ring-offset은 옛 색에 남는다.

참조를 풀려면 가리키는 대상이 Style Dictionary에 함께 있어야 한다. Semantic 파일만 넘기면 Some token references (3) could not be found. 오류로 빌드가 멈춘다. 그래서 Primitive를 함께 넘긴다. 다음 절은 함께 넘긴 Primitive가 출력에 섞이지 않게 하는 방법이다.

Primitive는 참조 대상으로만

Semantic 빌드에는 Primitive와 Semantic을 합친 객체를 넘긴다. 그대로 두면 Primitive도 출력 대상이라, Semantic 블록마다 Primitive 변수가 다시 나온다. file의 filter로 "Semantic 파일에 있는 토큰만" 고르면 Primitive는 참조를 푸는 데만 쓰이고 출력에서 빠진다. fixture의 light로 실행한 결과다.

filter 없음
:root {
  --gyeol-color-white: #ffffff;
  --gyeol-color-gray-900: #18181b;
  --gyeol-color-overlay: rgba(0, 0, 0, 0.5);
  --gyeol-spacing-4: 16px;
  --gyeol-radius-md: 6px;
  --gyeol-bg-surface: var(--gyeol-color-white);
  --gyeol-fg-default: var(--gyeol-color-gray-900);
  --gyeol-ring-offset: var(--gyeol-bg-surface);
}

Primitive가 맨 위 :root와 Semantic 블록 세 개에 모두 나온다. 같은 변수가 네 번 정의된다.

filter 있음hasTokenAt(semantic, token.path) 
:root {
  --gyeol-bg-surface: var(--gyeol-color-white);
  --gyeol-fg-default: var(--gyeol-color-gray-900);
  --gyeol-ring-offset: var(--gyeol-bg-surface);
}

Semantic만 나오고, 값은 여전히 Primitive를 var()로 가리킨다. 우리가 고른 방법이다.

hasTokenAt은 토큰의 경로(["bg-surface"], ["color", "white"])를 따라 Semantic 파일 객체를 내려가서, 그 자리에 $value가 있는 토큰이 있는지 본다. ["color", "white"]는 Semantic 파일에 없으므로 빠진다.

Style Dictionary에는 "참조 대상으로만 읽을 파일"을 받는 include 옵션이 있다. 하지만 include는 source처럼 경로를 glob으로 풀어, 파일이 없어도 오류를 내지 않는다(tokens와 source). 토큰 파일을 직접 읽는다는 방침과 맞지 않아 tokens + filter를 쓴다. 출력은 같다.

filter로 참조 대상을 빼면, Style Dictionary는 기본 로그에서 While building …, filtered out token references were found; output may be unexpected. 경고를 찍는다. 출력에 없는 변수(Primitive)를 가리킨다는 뜻이다. Primitive는 맨 위 :root에 따로 나오므로 의도한 동작이고, log.verbosity: "silent"라 보이지 않는다.

Semantic의 $type은 토큰마다

Primitive는 color 그룹에 $type: "color"를 한 번 적고 안의 토큰이 물려받는다. Semantic은 color 같은 범주 그룹이 없어서 물려받을 곳이 없다. 그래서 토큰마다 적는다. 

{
  "bg-surface": {
    "$type": "color",
    "$value": "{color.white}"
  },
  "ring-offset": {
    "$type": "color",
    "$value": "{bg-surface}"
  }
}

파일 맨 위에 $type을 한 번만 적는 방법도 검토했다. DTCG 2025.10은 "$value가 없는 객체는 group"이고 "group의 $type을 안의 토큰이 물려받는다"고 하지만, 파일 맨 위 객체가 group이라거나 거기에 $type을 둘 수 있다고 직접 말하지 않는다. 예시도 모두 이름 있는 group이나 토큰에 적는다. 도구가 받아 줄지 보장되지 않아 쓰지 않았다.

$type을 빼고 실행하면 CSS 출력은 같다. 하지만 Style Dictionary가 본 토큰의 $type은 undefined다. 참조 대상(color.white)의 타입을 물려받지 못한다(Style Dictionary 이슈 #1811). 지금은 참조가 이미 변환된 Primitive 값으로 풀려서 티가 나지 않을 뿐이다. color/css처럼 타입을 보고 걸리는 transform은 $type이 "color"인 토큰에만 걸리므로(isColor filter), 타입이 필요한 빌드에서는 이 토큰을 색으로 다루지 못한다.

Color Scheme 블록

fixture로 만든 CSS 전체다. 블록이 네 개이고, 위에서부터 Primitive, light, dark(OS 설정), dark(속성)다. 

/**
 * Do not edit directly, this file was auto-generated.
 */

:root {
  --gyeol-color-white: #ffffff;
  --gyeol-color-gray-900: #18181b;
  --gyeol-color-overlay: rgba(0, 0, 0, 0.5);
  --gyeol-spacing-4: 16px;
  --gyeol-radius-md: 6px;
}

:root {
  color-scheme: light;
  --gyeol-bg-surface: var(--gyeol-color-white);
  --gyeol-fg-default: var(--gyeol-color-gray-900);
  --gyeol-ring-offset: var(--gyeol-bg-surface);
}

  :root:not([data-color-scheme="light"]) {
    color-scheme: dark;
    --gyeol-bg-surface: var(--gyeol-color-gray-900);
    --gyeol-fg-default: var(--gyeol-color-white);
    --gyeol-ring-offset: var(--gyeol-bg-surface);

}

:root[data-color-scheme="dark"] {
  color-scheme: dark;
  --gyeol-bg-surface: var(--gyeol-color-gray-900);
  --gyeol-fg-default: var(--gyeol-color-white);

}
  • Primitive 블록은 Color Scheme과 관계없이 늘 같다. Semantic 블록만 Color Scheme마다 다른 Primitive를 가리킨다.
  • ring-offset은 세 블록 모두에서 다시 선언된다. 그래서 블록이 바뀔 때 그 블록의 bg-surface를 따라간다.
  • 블록마다 CSS color-scheme 속성이 있다. 스크롤바, 폼 컨트롤 같은 브라우저 기본 UI가 이 값을 보고 밝게 또는 어둡게 그려진다.

어떤 블록이 적용되나

갈림길은 두 개다. OS(웹뷰라면 네이티브 앱)의 설정, 그리고 <html>의 data-color-scheme 속성이다. 경우는 모두 여섯 가지다. 아래 표는 실제 tokens.css를 Chrome에 넣고 경우마다 <html>의 --gyeol-bg-surface와 color-scheme을 읽은 결과다(light는 #ffffff, dark는 #09090b).

light "dark" light :root, :root[data-color-scheme="dark"] 명시도가 높은 속성 블록이 이긴다 dark

블록 순서와 명시도

한 요소에 여러 블록이 맞으면 명시도(selector의 점수)가 높은 쪽이 이긴다. 같으면 뒤에 나온 쪽이 이긴다.

selector 명시도 계산
:root (0,1,0) 가상 클래스 1개
:root:not([data-color-scheme="light"]) (0,2,0) :root 1개 + :not() 안의 속성 selector 1개 :not() 자체는 점수가 없다
:root[data-color-scheme="dark"] (0,2,0) :root 1개 + 속성 selector 1개

dark 블록은 둘 다 (0,2,0)이라 light :root(0,1,0)를 블록 순서와 관계없이 이긴다. 그래서 블록 순서를 바꿔도 결과가 같다.

속성은 <html>에서만 동작한다

블록의 selector가 모두 :root로 시작하므로, <html>이 아닌 요소에 붙인 속성은 어느 블록에도 맞지 않는다. CSS 변수는 상속되므로 그 요소는 <html>의 값을 그대로 물려받는다. 위 여섯 경우 모두에서 <section data-color-scheme="dark">와 <section data-color-scheme="light">는 <html>과 같은 값이 나왔다.

페이지 일부만 다른 Color Scheme으로 바꾸는 것은 지원하지 않기로 했다. 처음에는 dark 속성 블록이 [data-color-scheme="dark"]여서 하위 요소에서 dark만 동작하고 light는 동작하지 않는 비대칭이 있었다. 모든 블록을 :root로 묶어 이 비대칭을 없앴다.

확인 방법: OS 설정은 페이지에서 바꿀 수 없어서, OS light는 @media 블록을 지운 CSS로, OS dark는 @media (…) { 감싸기만 벗긴 CSS로 확인했다. media 조건이 거짓일 때와 참일 때 브라우저가 보는 규칙과 같다.

직접 만든 format

Semantic 블록은 기본 format css/variables로 만들 수 없다. css/variables도 selector 옵션에 배열을 주면 @media 안에 :root를 중첩해 준다. 하지만 블록 안에 토큰이 아닌 줄(color-scheme: dark;)을 넣을 방법이 없다. 그래서 변수 줄 만드는 일만 Style Dictionary의 도우미 함수 formattedVariables에 맡기고, 나머지를 직접 짠다. 

const colorSchemeFormat =
  (colorScheme: ColorScheme, selectors: SelectorChain): FormatFn =>
  ({ dictionary }) => {
    const indent = indentAt(selectors.length);
    const variables = formattedVariables({
      format: "css",
      dictionary,
      outputReferences: true,
      usesDtcg: true,
      formatting: { indentation: indent },
    });
    const body = `${indent}color-scheme: ${colorScheme};\n${variables}`;
    const block = selectors.reduceRight(
      (content, selector, depth) =>
        `${indentAt(depth)}${selector} {\n${content}\n${indentAt(depth)}}`,
      body,
    );
    // css/variables처럼 줄바꿈으로 끝낸다
    return `${block}\n`;
  };
  1. 변수 줄 formattedVariables가 --이름: 값; 줄을 만든다. outputReferences: true라 참조는 var()로 나온다. 중첩 깊이만큼 들여 쓴다.
  2. color-scheme 줄 맨 앞에 color-scheme: light; 또는 dark;를 붙인다.
  3. selector로 감싸기 reduceRight로 안쪽 selector부터 감싼다. ["@media …", ":root:not(…)"]면 먼저 :root:not(…) { … }를 만들고, 그것을 다시 @media … { … }로 감싼다.
  4. 헤더 없음 css/variables와 달리 헤더를 붙이지 않는다. 헤더는 Primitive 블록(파일 맨 위)에 한 번만 나온다.

format은 이름으로 등록한다

Style Dictionary의 타입 선언은 file의 format에 함수도 받는다고 되어 있다(string | FormatFn). 그런데 5.8.0은 실제로 등록된 이름만 찾는다. 함수를 넣으면 Can't find format: … 오류가 난다(타입 검사는 통과하고 실행에서 실패한다). 그래서 블록마다 만든 함수에 gyeol/css/dark-0 같은 이름을 붙여 hooks.formats에 등록하고, file에는 그 이름을 적는다.

이름 selector 만드는 블록

gyeol/css/dark-0 ["@media (prefers-color-scheme: dark)", ':root:not([data-color-scheme="light"])'] dark (OS 설정)
gyeol/css/dark-1 [':root[data-color-scheme="dark"]'] dark (속성)

platforms와 prefix

platforms는 "같은 토큰으로 만들 출력"의 목록이다. 키는 우리가 정하는 이름이고, 값은 그 출력의 설정이다. CSS와 iOS를 함께 낸다면 css와 ios 두 키를 둔다. 지금은 CSS만 내므로 키가 하나다. formatPlatform("css")의 "css"가 이 키를 가리킨다.

prefix는 플랫폼 설정의 하나라 플랫폼마다 다르게 줄 수 있다. 이름을 만드는 transform(name/kebab)이 경로 앞에 붙인다.

설정 color.gray.900의 변수 이름
prefix: "gyeol" + name/kebab --gyeol-color-gray-900
prefix 없음 + name/kebab --color-gray-900
prefix: "gyeol" + name/camel --gyeolColorGray900
prefix: "gyeol" + 이름 transform 없음 prefix도 붙지 않는다 --900 충돌 위험

마지막 줄처럼 이름 transform이 없으면 경로의 마지막 조각만 이름이 되고, prefix도 쓰이지 않는다. spacing.4는 --4, radius.md는 --md가 되어 다른 범주의 같은 이름과 부딪힌다.

transformGroup과 transforms

transform은 토큰 하나를 받아 이름, 값, 속성 중 하나를 바꾸는 함수다. 두 옵션 중 하나로 고른다.

  • transforms: ["name/kebab", "color/css", …]: 쓸 transform을 직접 나열한다.
  • transformGroup: "css": Style Dictionary가 CSS용으로 묶어 둔 목록을 쓴다. 우리가 고른 방법이다.

transform마다 filter가 있어서, 맞는 토큰에만 걸린다. 예를 들어 color/css는 $type이 color인 토큰에만 걸린다. 그래서 group에 필요 없는 transform이 들어 있어도, 맞는 토큰이 없으면 아무 일도 하지 않는다. 아래 표는 css group의 14개 transform의 filter를 fixture 토큰에 직접 대 본 결과다.

attribute/cti 속성 모두 CSS는 같다 경로를 {category, type, item}으로 적어 둘 뿐이다
name/kebab 이름 모두 --white, --900, --4
color/css 값 color 3개 색이 [object Object]
size/rem 값 spacing.4, radius.md 크기가 [object Object]

실제로 일을 하는 것은 name/kebab, color/css, size/rem 세 개다. 나머지는 typography나 shadow 토큰이 생길 때 쓰인다. 직접 세 개만 나열해도 지금 출력은 같지만, 표준 묶음을 쓰면 Style Dictionary 문서와 바로 맞춰 읽을 수 있다.

files: format과 options

files는 플랫폼 하나에서 만들 파일의 목록이다. 항목마다 어떤 format으로 만들지(format), 어디에 쓸지 (destination), format에 넘길 옵션(options)을 적는다. 같은 토큰으로 CSS 파일 두 개를 만들고 싶으면 항목을 두 개 둔다.

css/variables format

transform이 끝난 토큰을 하나씩 --이름: 값; 줄로 만들어 선택자 블록 하나에 담는다. 기본값 그대로 둔 옵션과, 다음 티켓에서 쓸 옵션은 아래와 같다.

옵션 기본값 바꾸면
showFileHeader true false면 맨 위의 /** Do not edit directly, this file was auto-generated. */ 주석이 빠진다 Primitive 빌드는 기본값 그대로 둔다. 고정 문구라 snapshot이 빌드마다 바뀌지 않고, 배포되는 dist/tokens.css를 직접 고치지 말라는 표시가 된다. Semantic 블록은 직접 만든 format이 헤더를 내지 않아, 헤더는 파일 맨 위에 한 번만 나온다
selector :root "[data-x]"를 주면 블록이 [data-x] { … }로 나온다 배열을 주면 중첩한다. Semantic 블록은 이 옵션 대신 직접 만든 format으로 selector를 감싼다(직접 만든 format)

formatPlatform

설정을 만든 뒤 빌드를 시작하는 메서드는 여럿이다. 무엇을 돌려주고 파일을 기록하는지가 다르다.

메서드 돌려주는 것 파일 기록
buildAllPlatforms() 없음 기록함 모든 플랫폼

formatPlatform("css") [{ output, destination }] 파일마다 하나 안 함

2. 아래처럼 바꾸면 --gyeol-spacing-4는 무엇이 되나?

transformGroup과 transforms의 표로 생각한다. 

-        transformGroup: "css",
+        transforms: ["name/kebab", "color/css"],

--gyeol-spacing-4: [object Object];다. dimension 객체를 문자열로 바꿀 transform(size/rem이나 size/px)이 없다. 색은 그대로 나오고 오류도 나지 않는다. fixture snapshot 테스트가 이 변화를 잡는다.

3. 나중에 { "value": 1.5, "unit": "rem" } 토큰을 허용하게 되면, size/px와 size/rem 중 무엇이 맞게 내나?

size/rem이다. 적힌 unit을 지켜 1.5rem을 낸다. size/px는 unit을 무시하고 1.5px를 낸다.

5. buildSemanticCss에서 filter 줄을 지우면 tokens.css는 어떻게 되나?

6. OS 설정이 dark이고 <html>에 속성이 없다. 카드 하나를 밝게 보이려고 <div data-color-scheme="light">로 감쌌다. 카드의 --gyeol-bg-surface는?

Color Scheme 블록의 "속성은 <html>에서만 동작한다"로 생각한다.

답 보기

dark 값 그대로다. 모든 블록의 selector가 :root로 시작해서 <div>에 맞는 블록이 없고, 변수는 <html>의 dark 값을 물려받는다. 페이지 일부의 Color Scheme을 바꾸는 것은 지원하지 않는다.

7. 사이트의 다크 모드 토글이 <html>의 속성을 "light"로 바꿨다. 사용자의 OS는 dark다. 어느 블록이 적용되나?

Color Scheme 블록의 여섯 경우 표로 생각한다.

답 보기

light :root만 적용된다. media 조건은 참이지만 :root:not([data-color-scheme="light"])가 <html>에 맞지 않아 media 블록이 빠진다. 속성 블록은 "dark"일 때만 맞는다.

출처

이 노트의 출력과 콘솔 로그는 모두 Style Dictionary 5.8.0을 직접 실행해 확인했다. transform의 동작은 패키지 소스 lib/common/transforms.js의 size/rem, size/px 구현과 lib/common/transform-utils/default-filters.js의 isColor로, format을 이름으로만 찾는 동작은 lib/transform/config.js로도 확인했다. Color Scheme 블록의 여섯 경우는 생성된 tokens.css를 Chrome에 넣고 getComputedStyle로 읽어 확인했다.
