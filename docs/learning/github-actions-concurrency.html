GitHub Actions concurrency

같은 PR에 push를 연달아 하면 이전 CI는 어떻게 될까? concurrency group이 정하는 "실행 1개, 대기 1개" 규칙과, 이 저장소가 PR과 main에서 그룹을 다르게 나누는 이유.

개념

group: 이름이 같은 실행끼리 줄을 세운다

concurrency.group은 문자열이나 식이다. 식의 결과가 같은 워크플로 실행끼리 하나의 그룹이 된다. 한 그룹 안에서는 다음 규칙이 적용된다.

  • 실행 중은 최대 1개. 그룹에 실행 중인 것이 있으면 새 실행은 pending이 된다.
  • 대기도 최대 1개. 새 실행이 오면 이미 대기 중이던 실행은 취소되고, 새 실행이 그 자리를 차지한다. 대기열이 아니라 "다음 차례 자리 하나"에 가깝다.
  • 이름이 다른 그룹끼리는 상관없다. 서로 기다리지 않고 병렬로 돈다.

cancel-in-progress: 실행 중인 것까지 취소한다

기본값(false)에서는 실행 중인 것은 끝까지 돈다. true면 새 실행이 올 때 실행 중인 것도 취소하고 새 실행이 바로 돈다. 값에 식을 쓸 수 있어서 이벤트에 따라 다르게 정할 수 있다.

queue 옵션: 2026년 현재 문서에는 queue: max(대기 최대 100개)가 있다. 기본값 single이 위의 "대기 1개" 규칙이다. queue: max와 cancel-in-progress: true는 함께 쓸 수 없다. 이 저장소는 queue를 쓰지 않는다.

직접 눌러 보기

처음 설정은 이 저장소의 ci.yml과 같다. 실행 하나는 6초 걸린다고 가정한다. 해 볼 것:

  1. PR #7에 push를 빠르게 세 번 누른다. 앞의 실행이 취소되고 마지막 것만 남는다.
  2. main에 merge를 빠르게 세 번 누른다. 커밋마다 그룹이 달라 셋 다 끝까지 돈다.
  3. group을 ci-${{ github.ref }}로 바꾸고 다시 main에 merge를 세 번 누른다. 세 실행이 한 그룹에 들어가서 두 번째 실행은 대기하다가 세 번째에 밀려 취소된다. 그 커밋은 CI를 한 번도 거치지 않는다.

이 저장소의 선택

CI 워크플로

concurrency:
  group: ci-${{ github.event.pull_request.number || github.sha }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}
  • PR 이벤트: pull_request.number가 있으므로 그룹은 ci-<PR 번호>다. 같은 PR의 push끼리 묶이고, cancel-in-progress가 true라 새 push가 이전 실행을 취소한다. 결과를 기다리는 것은 마지막 커밋뿐이므로 이전 실행은 러너 시간만 쓴다.
  • main push 이벤트: PR 정보가 없어 a || b가 뒤쪽을 고르고, 그룹은 ci-<커밋 sha>가 된다. 커밋마다 그룹이 달라 연달아 merge돼도 서로 취소하지 않는다. main의 모든 커밋이 검사를 한 번씩 받는다.

PR 제목 워크플로

concurrency:
  group: pr-title-${{ github.event.pull_request.number }}
  cancel-in-progress: true

PR 이벤트에서만 돌기 때문에 PR 번호 하나로 충분하다. 제목을 여러 번 고치면 마지막 제목의 검사만 의미 있으므로 항상 이전 실행을 취소한다.

이 저장소에서 쓰인 곳

  • .github/workflows/ci.yml:12: PR과 main push에서 그룹을 다르게 나누는 식과 주석
  • .github/workflows/pr-title.yml:12: PR 번호로만 묶고 항상 취소
