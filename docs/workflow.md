# 워크플로우

[로드맵](./roadmap.md)의 항목을 구현하는 반복 절차와, 학습 노트를 쓰는 방법이다.

## 역할

- **에이전트**: 조사하고, 코드를 쓰고, 학습 노트를 쓴다.
- **사람**: 설계를 결정하고, 코드를 적극적으로 리뷰하고, 필요할 때 학습 노트를 요청한다.

## 단위

작업은 Phase → 스펙 → 티켓 → PR 순서로 나뉜다.

- **스펙**: 한 번의 설계 인터뷰로 결정을 끝낼 수 있는 작업 묶음이다(예: "토큰 파이프라인", "Button"). 로드맵의 항목 하나이고, spec 이슈 하나와 짝을 이룬다.
- **티켓**: 스펙을 나눈 조각이고, spec 이슈의 sub-issue다. 목적 하나를 이루고, 사람이 리뷰하기 적절한 크기이며, 따로 검증할 수 있는 조각이다. 티켓 하나가 PR 하나다. 사람이 PR마다 한 가지 목적만 놓고 꼼꼼히 리뷰할 수 있게 하려는 것이다.

`/to-tickets` 스킬은 티켓을 "vertical slice"라고 부른다. 이 저장소에서는 혼동을 피하려고 "슬라이스"라는 말을 쓰지 않는다.

Phase를 시작할 때는 Phase 전체에 걸친 규칙(예: 컴포넌트 폴더 구조)을 정하는 `/grill-with-docs`를 한 번 먼저 한다. 범위가 한 세션에 담기지 않으면 `/wayfinder`를 쓴다.

## 결정을 적는 곳

| 결정 | 적는 곳 |
|---|---|
| Phase 전체에 걸친 규칙 | [`docs/architecture.md`](./architecture.md) |
| 코드를 쓰고 리뷰할 때의 규칙(함수 인자 모양 등) | [`docs/coding-standards.md`](./coding-standards.md) |
| 스펙 하나 안에서 끝나는 결정 | spec 이슈의 Implementation Decisions |

| 용어 | [`GLOSSARY.md`](../GLOSSARY.md) |

## PR 나누기

- PR은 두 조건을 모두 만족하게 나눈다.
  - **목적 하나**: PR의 목적을 한 문장으로 쓸 수 있고 모든 변경이 그 목적을 위한 것이다. 그 한 문장이 PR 제목의 설명이 된다.
  - **사람이 리뷰하기 적절한 크기**: 사람이 한 번 앉아서 모든 변경을 읽고 이해할 수 있다.
- 예: oxlint, Prettier, pre-commit hook 설정은 "커밋 전에 코드 품질을 검사한다"는 목적 하나이고 한 번에 읽을 수 있어 PR 하나다.
- 예: 토큰 변환기와 Storybook 설정은 목적이 달라 PR을 나눈다.
- 예: 토큰 변환기 하나가 한 번에 읽기 어려울 만큼 크면, 목적을 더 작은 단계(예: 입력 읽기, CSS 변수 출력)로 나눠 PR을 나눈다.
- 크기에는 숫자 기준을 두지 않는다. 구현 중에 diff가 커지면 목적이 정말 하나인지, 한 번에 리뷰할 수 있는지 다시 보고, 나눌 수 있으면 사람에게 제안한다.
- 같은 문서를 고치는 PR이 있으면, 그 문서의 작은 정정은 함께 넣어도 된다.
- 티켓 하나가 PR 하나다. 저장소 밖의 일만 하는 사람 작업 티켓(`ready-for-human`, 예: 저장소 설정 변경)만 예외로, PR 없이 무엇을 했는지 댓글로 남기고 닫는다.
- 코드를 바꾸는 PR에는 반드시 티켓이 있다. 문서만 바꾸는 PR은 티켓 없이 열 수 있다.

## 스펙 반복

| 순서 | 하는 일 | 명령 | 결과물 |
|---|---|---|---|
| 1 | 로드맵에서 다음 스펙을 고른다 | 없음 | 스펙 범위 |
| 2 | 설계를 인터뷰로 정한다 | `/grill-with-docs` | `GLOSSARY.md`, `docs/adr/` 갱신 |
| 3 | 스펙을 이슈로 정리하고 티켓으로 나눈다 | `/to-spec`, `/to-tickets` | spec 이슈, 티켓(sub-issue) |
| 4 | 티켓을 구현한다 | `/implement <티켓>` | 티켓 브랜치의 커밋, PR |
| 5 | 사람이 리뷰한다 | 없음 | 리뷰 반영 커밋 |
| 6 | merge한다 | 없음 | `main` 반영 |
| 7 | 로드맵에 완료를 표시하고 spec 이슈를 닫는다 | 없음 | `docs/roadmap.md` 갱신 |

4~6은 티켓마다 반복한다. 7은 스펙의 마지막 PR에서 한다.

### 2. 설계 인터뷰

- 배경 학습과 사실 조사는 이 단계 안에서 한다. 에이전트는 필요한 사실(라이브러리 현황, 참고할 오픈소스 구현, 명세)을 직접 조사해서 질문과 함께 제시한다.

### 3. spec 이슈와 티켓

- 모든 스펙에서 `/to-spec`으로 spec 이슈를 만든다. 템플릿은 스킬을 따르되, 이 저장소에서는 다음을 지킨다.
  - 본문 첫 줄에 해당 로드맵 항목의 링크를 단다.
  - User Stories는 행위자(사용자 개발자, 디자이너, 기여자)별로 핵심만 짧게 쓴다. 템플릿의 영어 형식(`As a …, I want …, so that …`) 대신 "행위자로서, 원하는 것. 얻는 것" 형식의 한국어 문장으로 쓴다(예: "디자이너로서, 배포된 Storybook 링크로 토큰을 보고 싶다. 저장소 없이 Figma 값과 비교할 수 있다").
  - 중심은 Implementation Decisions다. 인터뷰에서 정했지만 ADR로 남기지 않는 결정을 빠짐없이 적는다.
- `/to-tickets`로 티켓을 spec 이슈의 sub-issue로 만든다. 티켓 본문에는 그 티켓의 What to build, 수용 기준, blocker만 적는다. 여러 티켓에 공통인 결정은 spec 이슈에만 둔다.

### 4. 구현

- `main`에서 티켓 브랜치 `ticket/<이슈 번호>-<이름>`(예: `ticket/12-token-build`)을 만들고 그 위에서 작업한다.
- 앞 티켓의 PR이 merge된 뒤에 다음 티켓을 시작한다. 서로 막지 않는 티켓은 동시에 진행해도 된다.
- `/implement`는 티켓과 함께 부모 spec 이슈를 읽고 작업한다.
- `/implement`는 내부에서 `tdd`와 `code-review` 스킬을 실행하고 현재 브랜치에 커밋한다. 따로 실행하지 않는다.
- `/implement-spec`은 쓰지 않는다. 모든 티켓을 통합 브랜치 하나에 모아 PR 하나로 내기 때문이다. 티켓마다 `/implement`를 따로 실행한다.
- 티켓을 구현하면 PR을 연다. PR 본문에 `Closes #<이슈 번호>`를 적어 merge할 때 티켓이 닫히게 한다.

### 5. 사람 리뷰

- 사람은 PR을 읽고 질문하고 수정을 요청한다. 에이전트의 `code-review`를 통과했다는 것이 사람 리뷰를 대신하지 않는다.
- 리뷰에서 설계가 바뀌면 에이전트는 리뷰 반영 커밋과 함께 spec 이슈의 Implementation Decisions를 고치고, 무엇이 왜 바뀌었는지 PR 링크와 함께 spec 이슈에 댓글로 남긴다. ADR 조건에 해당하면 ADR도 쓴다. 다음 티켓이 예전 결정을 따르지 않게 하려는 것이다.

### 6. merge

- PR은 squash merge만 한다. `main`은 CI 통과를 필수로 보호한다.
- 저장소 관리자는 `main` ruleset을 우회할 수 있다. 실수로 남은 설정이 아니라 일부러 둔 예외이므로 지우지 않는다. 관리자도 평소에는 PR로 merge한다.
- merge하면 PR 브랜치를 로컬과 원격 모두에서 지운다.
  - 원격: 저장소 설정 "Automatically delete head branches"가 켜져 있어 GitHub가 지운다.
  - CLI로 merge할 때는 저장소 폴더 안에서 `gh pr merge <번호> --squash --delete-branch`를 실행한다. 로컬 브랜치를 지우고 `main`으로 옮겨 최신으로 맞춘다. `--repo`를 붙이면 `gh`가 로컬 저장소를 건드리지 않아 로컬 브랜치가 남으므로 붙이지 않는다.
  - 웹에서 merge했으면 `git switch main && git pull`로 맞춘 뒤 `git branch -D <브랜치>`로 지운다. squash merge라 `main`의 이력에 브랜치 커밋이 없어서 `-d`는 거절된다.
  - 원격에서 지워진 브랜치의 추적 ref(`origin/<브랜치>`)는 `git fetch --prune`이 정리한다. `git config fetch.prune true`를 켜 두면 `git pull`할 때마다 정리된다.
- PR 제목은 Conventional Commit 형식으로 쓴다. release-please가 이 제목을 읽는다.
- scope는 패키지나 앱 이름(`tokens`, `tailwind`, `react`, `figma-plugin`, `storybook`)이다. 저장소 전체 변경에는 scope를 쓰지 않는다.
- PR 제목과 커밋 제목의 설명은 한국어로 쓰고, type과 scope는 영어 그대로 둔다(예: `ci: PR 제목 검사를 별도 워크플로로 분리`).

### 7. 스펙 마무리

- 스펙의 마지막 PR 본문에는 티켓과 함께 `Closes #<spec 이슈 번호>`도 적는다.
- 같은 PR에서 로드맵 항목에 완료를 표시하고 spec 이슈를 링크한다.
- 마지막 티켓이 PR 없이 닫는 사람 작업이면, 그 티켓을 닫을 때 spec 이슈도 댓글을 남기고 닫는다. 로드맵 갱신은 문서 PR로 한다.

## 학습 노트

학습 노트는 스펙 반복 절차에 들어 있지 않다. 사람이 필요할 때 주제를 정해 요청하면 에이전트가 쓴다.

- 노트는 HTML로 쓴다. 주제 하나가 파일 하나다. 만드는 방법, 모듈, 태그는 [`docs/learning/README.md`](./learning/README.md)를 따른다.
- 노트는 스펙이 아니라 **카테고리** 폴더(`docs/learning/<카테고리>/`)로 나눈다. 카테고리와 파일 이름은 사람이 정한다. 에이전트는 임의로 새 카테고리를 만들지 않고, 해당 카테고리 폴더가 이미 있으면 거기에 넣는다. 카테고리를 정하기 전의 노트는 `docs/learning/` 바로 아래에 둔다.
- 개념은 글로만 설명하지 않고 모듈(흐름도, 순서도, 시간 막대, 비교 카드 등)로 도식화한다. 설정이나 입력에 따라 결과가 갈리는 개념은 인터랙션 대신 경우의 수를 모두 펼쳐 보여 준다. 맞는 모듈이 없으면 모듈을 고치거나 새로 만든다.
- 모듈이 보여 주는 동작과 수치는 출처나 직접 실행으로 확인한 것만 쓴다.
- 노트마다 다음을 적는다: 개념 설명, 이 저장소에서 그 개념이 쓰인 코드 위치, 참고한 자료의 출처.

## 완료 조건

PR마다:

- CI의 lint, format 검사, typecheck, test, build가 통과한다.
- 변환 로직(토큰 변환, 아이콘 변환, Drift 비교)에는 Vitest 단위 테스트가 있다. 테스트 파일은 소스 옆에 `*.test.ts`로 둔다.
- 빌드 산출물(`dist`, 생성된 CSS)은 git에 넣지 않는다. 토큰 JSON과 Drift 검사의 기준이 되는 Figma 스냅샷은 넣는다.
- 새로 만들거나 사용법이 바뀐 패키지는 README에 사용법이 있다.

스펙마다:

- 로드맵에 완료를 표시했고, spec 이슈가 닫혔다.

## 의존성 버전

- 개발 의존성은 정확한 버전으로 고정한다. 자동 업데이트 도구는 쓰지 않고, Phase를 마칠 때 한 번에 올린다.
- 배포 패키지의 `peerDependencies`만 범위로 쓴다.

## Phase를 마칠 때

`/retro`로 에이전트 작업 환경(자동 검사, 코딩 규칙, 문서 포인터)을 점검하고 개선한다.
