squash merge와 release-please

이 저장소가 squash merge만 허용하고 squash 커밋 제목을 PR 제목으로 정한 이유. PR 제목 한 줄이 어떻게 다음 버전 번호와 CHANGELOG까지 이어지는지 다룬다.

release-please는 main의 커밋 제목을 읽는다

release-please는 마지막 릴리스 이후 기본 브랜치에 들어온 커밋을 Conventional Commit으로 읽는다. 그 결과로 다음 버전과 CHANGELOG를 담은 릴리스 PR을 열고, 릴리스 PR을 merge하면 태그와 GitHub Release를 만든다.

main의 커밋 제목이 곧 릴리스의 입력이다.

merge 방식이 main의 커밋을 정한다

같은 PR이라도 어떤 방식으로 merge하느냐에 따라 main에 남는 커밋이 다르다. 방식을 바꿔 보자. PR 브랜치에는 PR 안에서만 의미 있는 커밋(wip, 앞 커밋의 오타 수정)이 섞여 있다.

release-please README가 squash merge를 강하게 권하는 이유:

  • PR 안에서 feat: A 추가 뒤에 fix: A의 버그 수정을 했다면, 그 버그는 main에 존재한 적이 없다. 그런데 커밋이 그대로 들어가면 CHANGELOG에 버그 수정으로 올라간다.
  • 실패하는 테스트를 먼저 커밋하며 일하면, merge나 rebase는 테스트가 깨진 시점을 main에 남긴다.
  • merge 뒤에 릴리스 노트를 고치는 BEGIN_COMMIT_OVERRIDE는 PR 하나가 커밋 하나일 때만 동작한다. plain merge에서는 어느 커밋에 적용할지 알 수 없다.

main의 모든 커밋 제목이 CI가 검사한 PR 제목이다.

커밋 본문은 PR_BODY(PR 설명)를 쓴다. 그 밖의 값은 COMMIT_MESSAGES, BLANK다.

버전 계산해 보기

README 기준으로 feat는 minor, fix는 patch, type 뒤의 !(breaking)는 major를 올린다. 쌓인 커밋 중 가장 큰 변경 하나가 버전을 정한다. 릴리스를 만드는 커밋("releasable unit")은 feat, fix, deps이고, chore나 build만 쌓이면 릴리스 PR이 생기지 않는다.

1.0.0 미만에서는 옵션 두 개가 계산을 바꾼다. 둘 다 기본값은 false라서, 옵션 없이 0.x에서 breaking 커밋이 들어가면 곧바로 1.0.0이 된다. 옵션을 켜고 끄면서 feat(react)!: Button API 변경 같은 줄을 넣어 보자.

이 모듈은 커밋 제목만 본다. 커밋 본문의 BREAKING CHANGE: footer나 changelog-sections 설정으로 릴리스 대상 type을 바꾸는 경우는 다루지 않는다. 0.x에서 어떤 옵션을 쓸지는 로드맵의 "릴리스 기반" 슬라이스에서 정한다.

이 저장소에서 쓰인 곳

  • 저장소 설정(코드 밖): squash만 허용, squash_merge_commit_title: PR_TITLE, squash_merge_commit_message: PR_BODY. 확인하는 명령: gh api repos/gyeol-ui/gyeol-ui --jq '{allow_squash_merge, squash_merge_commit_title}'
  • ruleset main(코드 밖): PR 필수, allowed_merge_methods: ["squash"], 필수 검사 Check와 PR title
  • .github/workflows/pr-title.yml: PR 제목의 형식과 scope 검사
  • docs/workflow.md "6. merge": squash merge만 한다는 규칙과 PR 제목 규칙
