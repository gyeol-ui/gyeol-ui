Style Dictionary로 토큰을 CSS로 빌드하기

packages/tokens/scripts/build-tokens.ts의 buildTokens는 토큰 JSON을 읽어 CSS 텍스트를 돌려주는 함수다. Primitive는 실제 값으로, Semantic은 Color Scheme(light/dark) 블록마다 var() 참조로 낸다. 이 함수가 Style Dictionary에 넘기는 옵션을 하나씩 뜯어 보고, 옵션을 바꾸면 출력이 어떻게 달라지는지 직접 실행한 결과로 보여 준다.

한눈에 보기

파란 줄은 buildTokens 안에서 일어나는 일이다. Style Dictionary를 세 번 실행해 나온 CSS 블록을 이어 붙인다. 파일을 읽고 문자열을 돌려줄 뿐 파일을 기록하지 않는다. 초록 줄은 pnpm build가 이 함수를 실제 토큰 폴더로 불러 결과를 파일로 기록하고, tsdown이 dist/를 채우는 흐름이다.

buildTokens(토큰 폴더)
  1. 토큰 파일 3개가 있는지 확인한다
  2. 1번째 실행: Primitive → 헤더 + :root 블록
  3. 2번째 실행: Primitive(include) + light → light 블록
  4. 3번째 실행: Primitive(include) + dark → dark 블록 2개
  5. 블록 4개를 이어 { css }로 돌려준다
pnpm build
  1. build.ts: buildTokens("tokens/")
  2. build.ts: generated/tokens.css에 기록한다
  3. tsdown: dist/를 비우고 dist/index.js를 만든다
  4. tsdown: generated/tokens.css를 dist/로 복사한다

파일 기록을 함수 밖(build.ts)으로 뺀 이유는 테스트다. 테스트는 fixture 폴더로 buildTokens를 부르고 돌려받은 문자열만 검사한다. 디스크에 아무것도 남기지 않는다.

만들어지는 tokens.css

fixture로 만든 tokens.css 전체다. 블록이 네 개이고, 위에서부터 Primitive, light, dark(OS 설정), dark(속성)다. 

/**

 */

  --gyeol-color-gray-900: #18181b;
  --gyeol-color-overlay: rgba(0, 0, 0, 0.5);
  --gyeol-spacing-4: 16px;
  --gyeol-radius-md: 6px;

  color-scheme: light;
  --gyeol-bg-surface: var(--gyeol-color-white);
  --gyeol-fg-default: var(--gyeol-color-gray-900);
  --gyeol-ring-offset: var(--gyeol-bg-surface);
}

@media (prefers-color-scheme: dark) {
  :root:not([data-color-scheme="light"]) {
    color-scheme: dark;
    --gyeol-bg-surface: var(--gyeol-color-gray-900);
    --gyeol-fg-default: var(--gyeol-color-white);
    --gyeol-ring-offset: var(--gyeol-bg-surface);
  }
}

:root[data-color-scheme="dark"] {
  color-scheme: dark;
  --gyeol-bg-surface: var(--gyeol-color-gray-900);
  --gyeol-fg-default: var(--gyeol-color-white);
  --gyeol-ring-offset: var(--gyeol-bg-surface);
}
  • Primitive 블록은 Color Scheme과 관계없이 늘 같다. Semantic 블록만 Color Scheme마다 다른 Primitive를 가리킨다.
  • ring-offset은 세 블록 모두에서 다시 선언된다. 그래서 블록이 바뀔 때 그 블록의 bg-surface를 따라간다.
  • 블록마다 CSS color-scheme 속성이 있다. 스크롤바, 폼 컨트롤 같은 브라우저 기본 UI가 이 값을 보고 밝게 또는 어둡게 그려진다.

Style Dictionary가 하는 일

Style Dictionary는 플랫폼 중립의 토큰 JSON 하나를 플랫폼마다 다른 모양(CSS 변수, iOS Swift 상수, Android XML 등)으로 바꾸는 빌드 도구다. 바꾸는 일은 아래 순서로 나뉘고, 설정의 옵션은 각 단계에 무엇을 할지 알려 준다.

단계마다 붙인 결과물은 fixture로 light Semantic 빌드(Primitive는 include, semantic/light.json은 source)를 실제로 돌리며 Style Dictionary가 가진 값을 꺼낸 것이다. 길어서 일부 토큰만 옮겼다.

  1. 토큰 읽기 source와 include의 파일을 읽어 토큰 트리 하나로 합친다. $value가 보이면 DTCG 형식으로 판단한다(sd.usesDtcg가 true). 토큰마다 어느 파일에서 왔는지(filePath)와 source 파일인지(isSource)가 붙는다. 값은 아직 JSON에 적은 그대로다.
    파일 → 토큰 "bg-surface": { "$value": "{color.white}" }semantic/light.json 토큰 읽기 "bg-surface": { "$value": "{color.white}", "isSource": true, "filePath": "…/light.json" } 값은 그대로, 출처 표시가 붙는다

    ring-offset "{bg-surface}" 참조 해석 $value: "#ffffff" Semantic → Semantic도 끝까지 푼다

    // scripts/build.ts
await writeFile(join(generatedDir, "tokens.css"), css);

transform: 실제로 일하는 셋

transformGroup: "css"는 transform 14개로 풀린다(앞의 2단계 결과물). transform마다 filter가 있어서 맞는 토큰에만 걸린다. 예를 들어 color/css는 $type이 color인 토큰에만 걸린다. 우리 토큰(색, dimension)에 실제로 걸리는 것은 셋뿐이고, 나머지는 typography나 shadow 토큰이 생길 때 쓰인다.

transform 바꾸는 것 예 빼면
name/kebab 이름 ["color", "gray", "900"] → gyeol-color-gray-900 --900, --4처럼 경로의 마지막 조각만 남고 prefix도 붙지 않는다
color/css 색 값 색 객체 → #18181b, alpha가 있으면 rgba(0, 0, 0, 0.5) [object Object]
size/rem dimension 값 { value: 16, unit: "px" } → 16px [object Object]

transform이 빠져도 오류가 나지 않는다. Style Dictionary는 객체를 그대로 문자열로 바꿔 [object Object]를 낸다. 출력을 봐야 알 수 있어서 fixture 출력 전체를 snapshot으로 고정해 둔다.

color/css와 color/hex

alpha가 있는 색을 내는 방식이 다르다. fixture의 color.overlay(검정, alpha 0.5)로 실행한 결과다.

transform color.gray.900 color.overlay
color/css (css group) #18181b rgba(0, 0, 0, 0.5)
color/hex #18181b #00000080 alpha를 8자리 hex의 끝 두 자리로 낸다(80 = 128/255 ≈ 0.5)

spec이 "alpha가 있으면 rgba()"로 정해서 color/css가 맞다.

formatPlatform

설정을 만든 뒤 빌드를 시작하는 메서드는 여럿이다. 무엇을 돌려주고 파일을 기록하는지가 다르다.

메서드 돌려주는 것 파일 기록
buildAllPlatforms() 없음 기록함 모든 플랫폼
buildPlatform("css") 없음 기록함 플랫폼 하나
formatPlatform("css") [{ output, destination }] 파일마다 하나 안 함
getPlatformTokens("css") transform이 끝난 토큰 목록 (allTokens 등) 안 함

buildTokens는 "CSS 텍스트를 돌려주는" 함수라 formatPlatform이 맞다. dark 빌드처럼 files가 둘이면 배열에 항목도 둘이 온다. 실험에서 buildPath를 빈 폴더로 주고 formatPlatform만 불렀을 때 폴더가 생기지 않았다. getPlatformTokens는 앞의 Style Dictionary가 하는 일에서 transform 결과를 꺼낼 때 썼다.

참조가 var()가 되기까지

Semantic 토큰의 값은 실제 색이 아니라 다른 토큰을 가리키는 참조다. semantic/light.json의 bg-surface는 "{color.white}"이고, ring-offset은 다른 Semantic인 "{bg-surface}"다. 이 참조를 CSS에서도 참조(var())로 남기는 것이 Semantic 빌드의 핵심이다.

이름 ["bg-surface"]경로 name/kebab + prefix gyeol-bg-surface
Primitive 참조 "{color.white}" outputReferences var(--gyeol-color-white)
Semantic 참조 "{bg-surface}" outputReferences var(--gyeol-bg-surface) Semantic → Semantic도 같다
합치기 이름 + 값 createColorSchemeFormat --gyeol-bg-surface: var(--gyeol-color-white);

outputReferences를 켜지 않으면 Style Dictionary는 참조를 끝까지 풀어 실제 값을 낸다. fixture의 light로 두 경우를 실행한 결과다.

참조로 내기outputReferences: true
bg-surface
var(--gyeol-color-white)
ring-offset
var(--gyeol-bg-surface)

bg-surface를 바꾸면 ring-offset도 따라 바뀐다. Figma에서 Semantic이 다른 Semantic을 가리키던 구조가 CSS에도 남는다. 우리가 고른 방법이다.

값으로 풀기outputReferences: false
bg-surface
#ffffff
ring-offset
#ffffff

지금 보이는 색은 같지만 두 변수의 연결이 끊긴다. 누군가 --gyeol-bg-surface만 바꾸면 ring-offset은 옛 색에 남는다.

참조를 풀려면 가리키는 대상이 Style Dictionary에 함께 있어야 한다. Semantic 파일만 넘기면 Some token references (3) could not be found. 오류로 빌드가 멈춘다. 그래서 Primitive를 함께 넘긴다. 다음 절은 함께 넘긴 Primitive가 출력에 섞이지 않게 하는 방법이다.

Primitive는 참조 대상으로만

Semantic 빌드는 Primitive를 include로, Semantic을 source로 넘긴다. 둘 다 Style Dictionary가 읽는 파일 목록이고, 차이는 읽은 토큰에 붙는 표시 하나다.

옵션 넘기는 파일 토큰의 isSource
include primitive.json false
source semantic/light.json 또는 dark.json true

이름만 보면 include로 넣은 토큰은 출력되지 않을 것 같지만, 기본으로는 출력된다. file의 filter를 token.isSource로 두어야 Semantic만 나온다. fixture의 light로 실행한 결과다.

include만filter 없음 
:root {
  --gyeol-color-white: #ffffff;
  --gyeol-color-gray-900: #18181b;
  --gyeol-color-overlay: rgba(0, 0, 0, 0.5);
  --gyeol-spacing-4: 16px;
  --gyeol-radius-md: 6px;
  --gyeol-bg-surface: var(--gyeol-color-white);
  --gyeol-fg-default: var(--gyeol-color-gray-900);
  --gyeol-ring-offset: var(--gyeol-bg-surface);
}

Primitive가 맨 위 :root와 Semantic 블록 세 개에 모두 나온다. 같은 변수가 네 번 정의된다.

include + filterfilter: (token) => token.isSource 
:root {
  --gyeol-bg-surface: var(--gyeol-color-white);
  --gyeol-fg-default: var(--gyeol-color-gray-900);
  --gyeol-ring-offset: var(--gyeol-bg-surface);
}

Semantic만 나오고, 값은 여전히 Primitive를 var()로 가리킨다. 우리가 고른 방법이다.

filter로 참조 대상을 빼면, Style Dictionary는 기본 로그에서 While building …, filtered out token references were found; output may be unexpected. 경고를 찍는다. 출력에 없는 변수(Primitive)를 가리킨다는 뜻이다. Primitive는 맨 위 :root에 따로 나오므로 의도한 동작이고, log.verbosity: "silent"라 보이지 않는다.

Semantic의 $type은 토큰마다

Primitive는 color 그룹에 $type: "color"를 한 번 적고 안의 토큰이 물려받는다. Semantic은 color 같은 범주 그룹이 없어서 물려받을 곳이 없다. 그래서 토큰마다 적는다. 

{
  "bg-surface": {
    "$type": "color",
    "$value": "{color.white}"
  },
  "ring-offset": {
    "$type": "color",
    "$value": "{bg-surface}"
  }
}

파일 맨 위에 $type을 한 번만 적는 방법도 검토했다. DTCG 2025.10은 "$value가 없는 객체는 group"이고 "group의 $type을 안의 토큰이 물려받는다"고 하지만, 파일 맨 위 객체가 group이라거나 거기에 $type을 둘 수 있다고 직접 말하지 않는다. 예시도 모두 이름 있는 group이나 토큰에 적는다. 도구가 받아 줄지 보장되지 않아 쓰지 않았다.

$type을 빼고 실행하면 CSS 출력은 같다. 하지만 Style Dictionary가 본 토큰의 $type은 undefined다. 참조 대상(color.white)의 타입을 물려받지 못한다(Style Dictionary 이슈 #1811). 지금은 참조가 이미 변환된 Primitive 값으로 풀려서 티가 나지 않을 뿐이다. color/css처럼 타입을 보고 걸리는 transform은 $type이 "color"인 토큰에만 걸리므로(isColor filter), 타입이 필요한 빌드에서는 이 토큰을 색으로 다루지 못한다.

직접 만든 format

Semantic 블록은 기본 format css/variables로 만들 수 없다. css/variables도 selector 옵션에 배열을 주면 @media 안에 :root를 중첩해 준다. 하지만 블록 안에 토큰이 아닌 줄(color-scheme: dark;)을 넣을 방법이 없다. 그래서 변수 줄 만드는 일만 Style Dictionary의 도우미 함수 formattedVariables에 맡기고, 나머지를 직접 짠다. 

// build-tokens.ts
const createColorSchemeFormat =
  ({
    colorScheme,
    selectors,
  }: {
    colorScheme: ColorScheme;
    selectors: SelectorChain;
  }): FormatFn =>
  ({ dictionary }) =>
    wrapInColorSchemeBlock({
      colorScheme,
      selectors,
      // ① 변수 줄: Style Dictionary가 들여쓰기 없는 --이름: 값; 줄을 만든다
      variables: formattedVariables({
        format: "css",
        dictionary,
        outputReferences: true,
        usesDtcg: true,
        formatting: { indentation: "" },
      }),
    });

// build-tokens.helper.ts
export function wrapInColorSchemeBlock({
  colorScheme,
  selectors,
  variables,
}: {
  colorScheme: ColorScheme;
  selectors: SelectorChain;
  variables: string;
}): string {
  const indent = formatIndent(selectors.length);
  // ② color-scheme 줄을 맨 앞에 넣고, 줄마다 중첩 깊이만큼 들여 쓴다
  const body = [`color-scheme: ${colorScheme};`, ...variables.split("\n")]
    .map((line) => `${indent}${line}`)
    .join("\n");
  // ③ 안쪽 selector부터 감싼다
  const block = selectors.reduceRight(
    (content, selector, depth) =>
      `${formatIndent(depth)}${selector} {\n${content}\n${formatIndent(depth)}}`,
    body,
  );
  // ④ 헤더 없이 블록만 돌려준다
  return `${block}\n`;
}

코드의 ①~④ 주석이 아래 단계 번호와 같다.

  1. 변수 줄 formattedVariables가 들여쓰기 없는 --이름: 값; 줄을 만든다. outputReferences: true라 참조는 var()로 나온다. 여기까지가 Style Dictionary가 하는 일이다. dark의 OS 설정 블록(gyeol/css/dark-0)을 예로, 줄 하나만 따라가면 이렇다. 
    --gyeol-bg-surface: var(--gyeol-color-gray-900);
  2. color-scheme 줄과 들여쓰기 helper wrapInColorSchemeBlock이 맨 앞에 color-scheme: light; 또는 dark;를 붙이고, 줄마다 중첩 깊이만큼 들여 쓴다. selector가 둘이라 두 단계(공백 4칸) 들여 쓴다. 
        color-scheme: dark;
    --gyeol-bg-surface: var(--gyeol-color-gray-900);
  3. selector로 감싸기 reduceRight로 안쪽 selector부터 감싼다. ["@media …", ":root:not(…)"]면 먼저 :root:not(…) { … }를 만들고, 그것을 다시 @media … { … }로 감싼다. 
    @media (prefers-color-scheme: dark) {
  :root:not([data-color-scheme="light"]) {
    color-scheme: dark;
    --gyeol-bg-surface: var(--gyeol-color-gray-900);
  }
}
  4. 헤더 없음 css/variables와 달리 헤더를 붙이지 않는다. 헤더는 Primitive 블록(파일 맨 위)에 한 번만 나온다.

wrapInColorSchemeBlock이 어떤 입력을 어떤 블록으로 바꾸는지는 scripts/build-tokens.helper.test.ts에 입력과 출력 그대로 적혀 있다. 예를 들어 selector ["@media (prefers-color-scheme: dark)", ':root:not(…)']와 변수 줄 --gyeol-bg-surface: var(--gyeol-color-gray-900);를 넣으면 한눈에 보기의 tokens.css에 있는 media query 블록이 나온다.

format은 이름으로 등록한다

Style Dictionary의 타입 선언은 file의 format에 함수도 받는다고 되어 있다(string | FormatFn). 그런데 5.8.0은 실제로 등록된 이름만 찾는다. 함수를 넣으면 Can't find format: … 오류가 난다(타입 검사는 통과하고 실행에서 실패한다). 그래서 블록마다 만든 함수에 gyeol/css/dark-0 같은 이름을 붙여 hooks.formats에 등록하고, file에는 그 이름을 적는다.

이름 selector 만드는 블록
gyeol/css/light-0 [":root"] light
gyeol/css/dark-0 ["@media (prefers-color-scheme: dark)", ':root:not([data-color-scheme="light"])'] dark (OS 설정)
gyeol/css/dark-1 [':root[data-color-scheme="dark"]'] dark (속성)

스크립트를 위에서부터

build-tokens.ts는 아래 순서로 읽으면 된다. 함수가 여럿이지만 하는 일은 "Style Dictionary를 세 번 돌려 나온 CSS를 이어 붙인다" 하나다.

1. Color Scheme과 블록의 selector

// build-tokens.helper.ts
export const COLOR_SCHEMES = ["light", "dark"] as const;

export type ColorScheme = (typeof COLOR_SCHEMES)[number];

/** 바깥에서 안쪽 순서로 중첩하는 selector 목록. 예: `["@media …", ":root"]` */
export type SelectorChain = readonly string[];

// build-tokens.ts
const SCHEME_SELECTORS: Record<ColorScheme, readonly SelectorChain[]> = {
  light: [[":root"]],
  dark: [
    [
      "@media (prefers-color-scheme: dark)",
      ':root:not([data-color-scheme="light"])',
    ],
    [':root[data-color-scheme="dark"]'],
  ],
};
  • COLOR_SCHEMES는 빌드할 Color Scheme의 목록이자 CSS에 내는 순서다. 다른 helper도 쓰므로 build-tokens.helper.ts에 둔다. ColorScheme 타입("light" | "dark")도 이 배열에서 끌어내서, 목록을 한 곳에만 적는다.
  • SCHEME_SELECTORS는 Color Scheme마다 만들 CSS 블록의 selector다. light는 블록 1개, dark는 블록 2개(OS 설정, 속성)다. ["@media …", ":root:not(…)"]처럼 배열이면 앞의 것이 바깥, 뒤의 것이 안쪽인 중첩 블록이 된다. 이 selector가 브라우저에서 어떻게 적용되는지는 패키지 README의 "Color Scheme 고르기"에 있다.

2. 파일을 확인하고, 세 번 빌드해 이어 붙인다

export async function buildTokens(tokensDir: string): Promise<BuildResult> {
  // ① 파일이 있는지 확인한다: 토큰 파일 경로를 만들고 셋 다 있는지 본다
  const paths = resolveTokenFilePaths(tokensDir);

  // Style Dictionary의 source와 include는 경로 하나라도 glob 패턴으로 풀고, 맞는 파일이 0개여도 오류가 아니다.
  // 그러면 토큰 없이 빌드가 끝나 빈 블록이 나온다. 넘기기 전에 파일이 있는지 확인해, 없으면 ENOENT로 실패한다.
  for (const path of [paths.primitive, ...Object.values(paths.semantic)]) {
    await access(path);
  }

  // ② Primitive 블록을 만든다: 맨 위 헤더 + :root { 실제 값 }
  const cssBlocks = [await buildPrimitiveCss(paths.primitive)];
  // ③ Color Scheme마다 Semantic 블록을 만든다: light 1개, dark 2개
  for (const colorScheme of COLOR_SCHEMES) {
    cssBlocks.push(
      ...(await buildSemanticCss({
        primitivePath: paths.primitive,
        semanticPath: paths.semantic[colorScheme],
        colorScheme,
      })),
    );
  }
  // ④ 이어 붙인다: 블록 4개를 빈 줄 하나씩 두고 CSS 텍스트 하나로
  return { css: cssBlocks.join("\n").trimEnd() + "\n" };
}

이 함수가 전체 흐름이다. 코드의 ①~④ 주석이 아래 단계 번호와 같다.

  1. 파일이 있는지 확인한다 helper resolveTokenFilePaths가 primitive.json, semantic/light.json, semantic/dark.json의 경로를 만들고, access로 셋 다 있는지 본다. 읽는 일은 Style Dictionary가 하는데 왜 확인만 따로 하는지는 바로 다음 절 파일이 없을 때에 있다.
  2. Primitive 블록을 만든다 buildPrimitiveCss가 맨 위 헤더와 :root { --gyeol-color-…: #…; }를 만든다.
  3. Color Scheme마다 Semantic 블록을 만든다 light, dark 순서로 Primitive 경로와 그 Color Scheme의 Semantic 경로를 buildSemanticCss에 넘긴다. light는 블록 1개, dark는 블록 2개를 돌려준다.
  4. 이어 붙인다 블록 4개를 빈 줄 하나씩 두고 이어 붙여 CSS 텍스트 하나로 돌려준다.

3. Primitive: 지난 티켓과 같은 설정

/** Primitive와 Semantic 빌드가 함께 쓰는 CSS 플랫폼 설정. 만들 파일 목록만 다르다 */
const configureCssPlatform = (files: File[]): PlatformConfig => ({
  prefix: PREFIX,
  // 실제로 일하는 transform은 name/kebab(이름), color/css(hex, rgba()), size/rem(dimension)이다.
  // size/rem은 이름과 달리 px를 rem으로 바꾸지 않는다. unit이 적혀 있으면 그대로 붙이고
  // ({16, "px"} → "16px"), unit 없는 숫자에만 "rem"을 붙인다. 토큰은 모두 px로 쓰므로 px로 나온다.
  // size/px를 직접 고르지 않는 이유: size/px는 unit을 무시해 {1.5, "rem"}도 "1.5px"로 낸다.
  transformGroup: "css",
  files,
});

async function buildPrimitiveCss(primitivePath: string): Promise<string> {
  const sd = new StyleDictionary({
    source: [primitivePath],
    log: { verbosity: "silent" },
    platforms: {
      css: configureCssPlatform([{ format: "css/variables" }]),
    },
  });
  return (await formatOutputs(sd)).join("");
}

Primitive와 Semantic 빌드가 함께 쓰는 플랫폼 설정(prefix, transformGroup)은 configureCssPlatform으로 뺐다. Primitive 빌드는 기본 format css/variables를 그대로 써서, 파일 맨 위 헤더(Do not edit directly…)와 :root 블록을 만든다. 각 옵션이 하는 일은 아래 표와 같다.

옵션 값 하는 일
source [primitivePath] 빌드할 토큰 파일. Style Dictionary가 읽는다 파일이 없을 때
log.verbosity "silent" Style Dictionary의 콘솔 출력을 끈다 log.verbosity
platforms.css 설정 객체 "css"라는 이름의 출력 하나. 이름은 우리가 정한다 transform
prefix "gyeol" 변수 이름 앞에 붙일 말
transformGroup "css" CSS용으로 미리 묶어 둔 transform 14개를 쓴다 transformGroup과 transforms
files[].format "css/variables" 토큰 목록을 :root { … } 문자열로 만든다 직접 만든 format

4. Semantic: Primitive를 함께 넘기고 Semantic만 낸다

async function buildSemanticCss({
  primitivePath,
  semanticPath,
  colorScheme,
}: {
  primitivePath: string;
  semanticPath: string;
  colorScheme: ColorScheme;
}): Promise<string[]> {
  // 블록마다 selector가 달라 format을 블록마다 만든다.
  // 파일 설정의 format은 타입상 함수도 받지만 5.8은 등록된 이름만 찾으므로 이름을 붙여 등록한다.
  // ① format: 블록마다 직접 만든 format을 이름 붙여 만든다
  const formats = SCHEME_SELECTORS[colorScheme].map((selectors, index) => ({
    name: `gyeol/css/${colorScheme}-${index}`,
    format: createColorSchemeFormat({ colorScheme, selectors }),
  }));

  const sd = new StyleDictionary({
    // ② 토큰: Primitive는 참조를 푸는 데만, Semantic은 출력할 토큰
    include: [primitivePath],
    source: [semanticPath],
    log: { verbosity: "silent" },
    hooks: {
      // ① 만든 format을 이름으로 등록한다
      formats: Object.fromEntries(formats.map((f) => [f.name, f.format])),
    },
    platforms: {
      css: configureCssPlatform(
        formats.map(({ name }) => ({
          format: name,
          // ③ filter: source(Semantic)에서 읽은 토큰만 낸다
          filter: (token: TransformedToken) => token.isSource,
        })),
      ),
    },
  });
  return formatOutputs(sd);
}

Primitive 빌드와 다른 곳은 세 군데다. 코드의 ①~③ 주석이 아래 표의 번호와 같다.

다른 곳 코드 이유
① format createColorSchemeFormat(…)을 hooks.formats에 이름 붙여 등록 블록마다 color-scheme 속성을 넣고 헤더를 빼야 해서 직접 만든 format을 쓴다 직접 만든 format
② 토큰 include: [primitivePath], source: [semanticPath] Semantic은 {color.white}처럼 Primitive를 가리킨다. 가리키는 대상이 함께 있어야 참조가 풀린다 참조가 var()가 되기까지
③ filter (token) => token.isSource include로 넣은 Primitive도 기본으로 출력되므로, source(Semantic)에서 읽은 토큰만 낸다 Primitive는 참조 대상으로만

dark는 SCHEME_SELECTORS.dark에 selector가 두 개라 files도 두 개가 된다. 한 번 실행으로 내용이 같은 블록 두 개(media query 블록, 속성 블록)를 받는다.

5. 문자열만 받아 돌려준다

const formatOutputs = async (sd: StyleDictionary): Promise<string[]> => {
  const files = await sd.formatPlatform("css");
  return files.map(({ output }) => {
    if (typeof output !== "string") {
      throw new Error("Style Dictionary가 CSS를 만들지 못했다");
    }
    return output;
  });
};

formatPlatform은 files의 항목마다 { output, destination }을 담은 배열을 돌려준다. dark처럼 파일이 둘이면 항목도 둘이다. output의 타입은 문자열이 아닐 수도 있게 넓게 선언되어 있어서, 문자열인지 확인한 뒤 돌려준다. 다른 메서드와의 차이는 앞의 formatPlatform에서 보았다.

파일이 없을 때

Style Dictionary는 source와 include의 항목마다 globSync(패턴)으로 맞는 파일 목록을 구한다(lib/utils/combineJSON.js). 와일드카드 없는 경로도 패턴 하나로 다루고, glob은 "맞는 파일이 0개"를 오류가 아닌 빈 목록으로 돌려준다. 그래서 파일 이름을 틀리거나 파일이 없어도 Style Dictionary는 "파일이 없다"고 알려 주지 않는다. 없는 경로를 넣고 실행한 결과다.

없는 파일 Style Dictionary만 쓰면 먼저 access로 확인하면
primitive.json (Primitive 빌드의 source) 오류 없이 빈 :root {} 조용히 성공 ENOENT: no such file or directory, access '…/파일' 어떤 파일이 없는지 경로가 나온다
semantic/light.json (source) filter에 맞는 토큰이 없어 결과가 비고, 우리 코드가 "Style Dictionary가 CSS를 만들지 못했다"로 실패 원인이 파일이라는 말이 없다
primitive.json (Semantic 빌드의 include) Some token references (3) could not be found. 참조가 틀린 것처럼 보인다

그래서 buildTokens는 경로를 넘기기 전에 access로 세 파일이 있는지 확인한다. 이 동작은 테스트 "토큰 폴더에 primitive.json이 없으면 실패한다"와 "토큰 폴더에 Semantic 파일이 없으면 실패한다"가 지킨다.

처음 구현은 이 문제를 피하려고 파일을 직접 읽어 tokens 옵션에 객체로 넘기고, Semantic만 고르는 filter 함수도 직접 짰다. 지금은 파일이 있는지만 우리 코드가 확인하고, 읽기와 Semantic 고르기는 Style Dictionary의 source, include, isSource에 맡긴다.

출처

이 노트의 출력과 콘솔 로그는 모두 Style Dictionary 5.8.0을 직접 실행해 확인했다. transform의 동작은 패키지 소스 lib/common/transforms.js의 size/rem, size/px 구현과 lib/common/transform-utils/default-filters.js의 isColor로, format을 이름으로만 찾는 동작은 lib/transform/config.js로도 확인했다.

  • Style Dictionary, Architecture: 토큰 읽기, transform, 참조 해석, format, 기록의 순서
  • Style Dictionary, Config: tokens, source, log, platforms, prefix, transformGroup, files
  • Style Dictionary, Logging: verbosity의 값
  • Style Dictionary, Predefined transforms와 Predefined transform groups: name/kebab, color/css, size/rem, size/px와 css group의 구성
  • Style Dictionary, Predefined formats: css/variables와 showFileHeader, selector, outputReferences 옵션
  • Style Dictionary, API: formatPlatform, buildPlatform, getPlatformTokens
  • Style Dictionary, DTCG support: $value로 DTCG 형식을 알아보는 동작
  • Style Dictionary, 이슈 #1811: $type 없는 alias가 참조 대상의 타입을 물려받지 못하는 문제
  • Design Tokens Community Group, Design Tokens Format Module 2025.10: group의 정의(§6.1), group의 $type 상속(§5.2.2, §6.3)
