# 워크플로우

[로드맵](./roadmap.md)의 항목을 구현하고 학습 노트로 남기기까지의 반복 절차다.

## 역할

- **에이전트**: 조사하고, 코드를 쓰고, 학습 노트를 쓴다.
- **사람**: 설계를 결정하고, 코드를 적극적으로 리뷰하고, 학습 노트에 무엇을 적을지 정한다.

## 단위

반복 단위는 Phase가 아니라 **슬라이스**다. 슬라이스는 "토큰 파이프라인", "Button"처럼 한 번의 설계 인터뷰로 다룰 수 있는 조각이다.

슬라이스는 **티켓** 여러 개로 나뉜다. 티켓은 따로 검증할 수 있는 가장 작은 조각이고, 티켓 하나가 PR 하나다. PR을 작게 유지해 사람이 꼼꼼히 리뷰할 수 있게 하려는 것이다.

Phase를 시작할 때는 Phase 전체에 걸친 규칙(예: 컴포넌트 폴더 구조)을 정하는 `/grill-with-docs`를 한 번 먼저 한다. 범위가 한 세션에 담기지 않으면 `/wayfinder`를 쓴다.

## 슬라이스 반복

| 순서 | 하는 일 | 명령 | 결과물 |
|---|---|---|---|
| 1 | 로드맵에서 다음 슬라이스를 고른다 | 없음 | 슬라이스 범위 |
| 2 | 설계를 인터뷰로 정한다 | `/grill-with-docs` | `GLOSSARY.md`, `docs/adr/` 갱신, 학습 후보 |
| 3 | 티켓으로 나눈다 | `/to-spec`(큰 슬라이스만), `/to-tickets` | GitHub 이슈 |
| 4 | 티켓을 구현한다 | `/implement <티켓>` | 티켓 브랜치의 커밋, PR |
| 5 | 사람이 리뷰한다 | 없음 | 리뷰 반영 커밋 |
| 6 | merge한다 | 없음 | `main` 반영 |
| 7 | 학습 노트를 마무리하고 로드맵에 표시한다 | 없음 | `docs/learning/` HTML 노트 |

4~6은 티켓마다 반복한다. 7은 슬라이스의 마지막 티켓에서 한 번 한다.

### 2. 설계 인터뷰

- 배경 학습과 사실 조사는 이 단계 안에서 한다. 에이전트는 필요한 사실(라이브러리 현황, 참고할 오픈소스 구현, 명세)을 직접 조사해서 질문과 함께 제시한다.
- 사람이 모른다고 말한 개념과 "이건 적어 두자"고 한 내용은, 에이전트가 그 자리에서 `docs/learning/candidates.md`의 **학습 후보** 목록에 추가한다.

### 4. 구현

- `main`에서 티켓 브랜치 `ticket/<이슈 번호>-<이름>`(예: `ticket/12-token-build`)을 만들고 그 위에서 작업한다.
- 앞 티켓의 PR이 merge된 뒤에 다음 티켓을 시작한다. 서로 막지 않는 티켓은 동시에 진행해도 된다.
- `/implement`는 내부에서 `tdd`와 `code-review` 스킬을 실행하고 현재 브랜치에 커밋한다. 따로 실행하지 않는다.
- 티켓을 구현하면 PR을 연다. PR 본문에 `Closes #<이슈 번호>`를 적어 merge할 때 티켓이 닫히게 한다.

### 5. 사람 리뷰

- 사람은 PR을 읽고 질문하고 수정을 요청한다. 에이전트의 `code-review`를 통과했다는 것이 사람 리뷰를 대신하지 않는다.
- 리뷰 중 나온 질문과 답, 새로 알게 된 개념도 **학습 후보**에 추가한다.

### 6. merge

- PR은 squash merge만 한다. `main`은 CI 통과를 필수로 보호한다.
- 저장소 관리자는 `main` ruleset을 우회할 수 있다. 실수로 남은 설정이 아니라 일부러 둔 예외이므로 지우지 않는다. 관리자도 평소에는 PR로 merge한다.
- PR 제목은 Conventional Commit 형식으로 쓴다. release-please가 이 제목을 읽는다.
- scope는 패키지나 앱 이름(`tokens`, `tailwind`, `react`, `figma-plugin`, `storybook`)이다. 저장소 전체 변경에는 scope를 쓰지 않는다.
- PR 제목과 커밋 제목의 설명은 한국어로 쓰고, type과 scope는 영어 그대로 둔다(예: `ci: PR 제목 검사를 별도 워크플로로 분리`).

### 7. 학습 노트

- 노트는 HTML로 쓴다. 주제 하나가 파일 하나다. 만드는 방법, 모듈, 태그는 [`docs/learning/README.md`](./learning/README.md)를 따른다.
- 노트는 슬라이스가 아니라 **카테고리** 폴더(`docs/learning/<카테고리>/`)로 나눈다. 카테고리와 파일 이름은 사람이 정한다. 에이전트는 임의로 새 카테고리를 만들지 않는다. 카테고리를 정하기 전의 노트는 `docs/learning/` 바로 아래에 둔다.
- 개념은 글로만 설명하지 않고 모듈(흐름도, 순서도, 시간 막대, 인터랙티브 모듈 등)로 도식화한다. 맞는 모듈이 없으면 모듈을 고치거나 새로 만든다.
- 모듈이 보여 주는 동작과 수치는 출처나 직접 실행으로 확인한 것만 쓴다.
- 사람이 **학습 후보** 중 무엇을 적을지, 어느 카테고리에 넣을지 고르고, 에이전트가 쓴다. 해당 카테고리 폴더가 이미 있으면 거기에 넣는다.
- 고른 주제마다 다음을 적는다: 개념 설명, 이 저장소에서 그 개념이 쓰인 코드 위치, 참고한 자료의 출처.
- 노트에 옮긴 항목은 `docs/learning/candidates.md`에서 지운다.
- 노트는 슬라이스의 마지막 티켓 PR에 함께 넣는다.

## 완료 조건

PR마다:

- CI의 lint, format 검사, typecheck, test, build가 통과한다.
- 변환 로직(토큰 변환, 아이콘 변환, Drift 비교)에는 Vitest 단위 테스트가 있다. 테스트 파일은 소스 옆에 `*.test.ts`로 둔다.
- 빌드 산출물(`dist`, 생성된 CSS)은 git에 넣지 않는다. 토큰 JSON과 Drift 검사의 기준이 되는 Figma 스냅샷은 넣는다.
- 새로 만들거나 사용법이 바뀐 패키지는 README에 사용법이 있다.

슬라이스마다:

- 학습 노트를 마무리하고 로드맵에 표시했다.

## 의존성 버전

- 개발 의존성은 정확한 버전으로 고정한다. 자동 업데이트 도구는 쓰지 않고, Phase를 마칠 때 한 번에 올린다.
- 배포 패키지의 `peerDependencies`만 범위로 쓴다.

## Phase를 마칠 때

`/retro`로 에이전트 작업 환경(자동 검사, 코딩 규칙, 문서 포인터)을 점검하고 개선한다.
