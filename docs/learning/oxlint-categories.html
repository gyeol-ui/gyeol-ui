oxlint 규칙 범주

oxlint는 규칙 수백 개를 의도에 따라 7개 범주로 나눈다. 범주 단위로 켜고 끄는 방법과, 이 저장소가 correctness와 suspicious만 error로 켠 기준을 다룬다.

범주: 의도가 비슷한 규칙 묶음

.oxlintrc.json의 categories로 범주 하나를 통째로 켜거나 끈다. 값은 "error", "warn", "off"다. 특정 규칙만 다르게 하려면 rules에 적는다. rules가 categories보다 우선한다. 

{
  "categories": {
    "correctness": "error",
    "suspicious": "error",
    "pedantic": "off"
  },
  "rules": {
    "eslint/eqeqeq": "error"
  }
}

범주는 "이 코드가 틀렸을 확률"이 높은 쪽부터 "팀이 정하기 나름"인 쪽까지 늘어서 있다. 아래 표는 위에서부터 그 순서이고, nursery는 안정성이 다른 축이라 맨 끝에 둔다. 설정 파일이 없으면 oxlint는 correctness만 warn으로 켠다. 설정 없이 debugger; 한 줄을 검사하면 warning eslint(no-debugger)가 나온다.

규칙 수는 oxlint 1.94.0의 oxlint --rules --format=json 출력에서 센, 등록된 전체 규칙 수다. 기본으로 꺼진 플러그인(react, import 등)의 규칙도 포함하므로 실제로 켜지는 수는 더 적다. 이 저장소에서 켜진 규칙은 correctness 111개, suspicious 43개다.

warn과 error의 차이는 CI에서 드러난다

warn
출력
warning eslint(...)
종료 코드
0 (--deny-warnings를 주면 1)

CI와 pre-commit hook이 막지 못하고 출력만 남는다.

error이 저장소
출력
error eslint(...)
종료 코드
1

CI가 실패하고 커밋이 막힌다. 켜진 규칙은 반드시 지켜진다.

종료 코드는 oxlint 1.94.0으로 직접 확인했다. 이 저장소는 켠 범주를 모두 error로 둔다.

범주를 고르는 기준

범주 설정 이유
correctness, suspicious error 걸리면 대부분 실제 버그다. 오탐이 드물어 막아도 일에 방해가 되지 않는다.
pedantic off 문서가 "오탐이 있을 수 있다"고 밝힌 범주다. 쓸 만한 규칙은 rules에서 하나씩 켠다.
style off 형식이 아니라 관용 표현(prefer-const, curly)에 관한 규칙이다. 형식은 Prettier가 맡고, 관용 표현은 아직 팀 규칙을 정하지 않았다.
restriction off no-console, no-var처럼 특정 기능을 금지한다. 무엇을 금지할지는 프로젝트마다 달라서 범주째 켜기보다 필요한 규칙만 고른다.
perf off 아직 성능이 문제 될 코드가 없다. 컴포넌트가 생기면 다시 본다.
nursery off 개발 중이라 동작이 바뀔 수 있다. CLI의 all도 nursery는 빼고 켠다.

타입 인식 lint

options.typeAware: true를 켜면 oxlint-tsgolint가 TypeScript 타입 정보를 써서 검사한다. typescript/no-floating-promises(처리하지 않은 Promise)처럼 타입을 알아야 판단할 수 있는 규칙이 여기에 속한다. 이 규칙은 correctness 범주라 이 저장소에서 error로 켜져 있다.

이 저장소에서 쓰인 곳
