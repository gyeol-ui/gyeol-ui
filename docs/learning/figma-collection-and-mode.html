Figma Variables의 collection과 mode

Figma Variables는 값을 표에 적어 두고 화면에서 그 이름으로 쓰는 기능이다. 표 한 장이 collection, 표의 열이 mode다. 이 그림 하나로 gyeol-ui가 토큰을 왜 Primitive와 Semantic 표 두 장으로 나눴는지, 그 표가 어떻게 JSON 파일과 CSS 블록이 되는지까지 설명한다.

한눈에 보기

파란 줄은 Figma의 세 개념을 작은 것부터 큰 것 순으로 놓았다. 초록 줄은 그 각각이 gyeol-ui 코드에서 무엇이 되는지다.

Figma 안
  1. Variable: 이름이 붙은 값 하나
  2. Mode: 그 값의 버전 하나 = 표의 열
  3. Collection: 같은 열을 가진 Variable 묶음 = 표 한 장
gyeol-ui 코드
  1. Variable 하나 = Design Token 하나
  2. 열 하나 = JSON 파일 하나 = CSS 블록 하나
  3. Collection 하나 = 토큰 폴더 하나

이 문서 전체에서 기억할 그림은 하나다. Collection은 표, Mode는 그 표의 열, Variable은 행이다.

Variable: 이름이 붙은 값 하나

Figma에서 버튼을 파랗게 칠할 때 #2F62B5를 직접 고르지 않고, color/blue/500이라는 이름의 Variable을 만들어 그 Variable로 칠한다. 그러면 버튼은 "파란색"이 아니라 "blue 500"을 기억한다.

이득은 값을 바꿀 때 드러난다. Variable의 값을 한 번 바꾸면 그 Variable을 쓴 모든 화면이 한꺼번에 바뀐다. 아래는 같은 화면에서 color/blue/500의 값만 바꾼 두 경우다.

코드의 Design Token과 같은 개념이다. Variable의 값 종류는 색, 숫자, 문자열, 참/거짓이 기본이다. 간격 16은 숫자 Variable이다.

이름의 /는 폴더다

Variable 이름에 /를 넣으면 Figma가 그 앞부분을 그룹(폴더)으로 묶어 보여 준다. gyeol-ui는 Primitive 이름을 범주 → 이름 순으로 짓는다. Semantic은 색만 담으므로 범주 없이 이름만 쓰고, 필요하면 그룹을 한 단계 둔다. 이름 안의 단어는 -로 잇는다(kebab-case).

  • Primitive 표
    • color 범주 색
      • gray 회색 계열
        • 900 전체 이름 color/gray/900, 코드에서는 color.gray.900
    • spacing 범주 간격
      • 4 spacing/4 = 16 (4px의 4배)
  • Semantic 표
    • bg-surface 이름 화면 바탕. 폴더 없이 바로 놓인다
    • alpha 그룹 바탕색의 투명도 단계
      • 90 alpha/90 = 바탕색을 불투명도 90%로

Mode: 같은 Variable이 가진 값의 버전

Variable 하나가 값을 여러 개 가질 수 있다. 다크 모드를 예로 들면, 배경색 Variable은 밝은 화면용 흰색과 어두운 화면용 검정을 둘 다 가진다. 이 버전 하나하나가 Mode다.

Figma의 Variables 창은 이것을 표로 보여 준다. 행이 Variable이고, Mode는 열이다. 맨 왼쪽 열이 기본 Mode다. Mode를 새로 만들면 Figma가 첫 열의 값을 복사해 새 열을 만들고, 사용자는 그 열의 값을 고친다.

어떤 collection 값을 직접 적은 가장 단순한 경우
Variable modelight modedark
bg-surface #FAFAFA #18181B
fg-default #18181B #FAFAFA
border-default #E4E4E7 #3F3F46

행은 Variable, 열은 Mode다. 칸 하나가 "그 Variable의 그 Mode 값"이다.

화면(frame)마다 어느 열을 쓸지 정할 수 있다. 같은 화면을 light 열로 보면 왼쪽, dark 열로 보면 오른쪽이 된다. 디자이너는 다크 모드 시안을 따로 그리지 않고 열만 바꾼다.

"Mode"는 다크 모드의 그 모드가 아니다. Figma에서 Mode는 "표의 열"이라는 일반 개념이다. 열이 light/dark일 수도 있고, 화면 크기일 수도 있다.

Collection: 같은 열을 가진 Variable 묶음

Collection은 위와 같은 표 한 장이다. 규칙이 하나 있다. 표 하나 안의 모든 행은 같은 열을 가진다. light/dark 열이 있는 표에 Variable을 넣으면, 그 Variable도 light 값과 dark 값을 둘 다 적어야 한다.

그래서 열과 상관없는 값을 이 표에 넣으면 어색해진다. 간격 16은 밝은 화면에서도 어두운 화면에서도 16이다. 그런데 표의 규칙 때문에 두 열에 같은 값을 두 번 적어야 한다.

light/dark 열을 가진 collection에 간격을 넣으면 어색한 경우
Variable modelight modedark
bg-surface #FAFAFA #18181B
spacing/4 16 16

간격은 명암과 무관한데 열마다 값을 적어야 한다. 그래서 gyeol-ui는 간격을 이 표에 넣지 않고, 열이 하나뿐인 Primitive 표에 둔다.

정리하면, 어떤 값이 무엇에 따라 바뀌는가가 그 Variable이 들어갈 표를 정한다. 명암에 따라 바뀌면 열이 light/dark인 Semantic 표, 아무것에도 따라 바뀌지 않으면 열이 하나인 Primitive 표다.

Alias: 값 대신 다른 Variable을 가리키기

칸에는 값을 직접 적는 대신 다른 Variable을 가리키게 할 수도 있다. 이것을 alias라고 한다. 다른 collection의 Variable도, 같은 collection의 Variable도 가리킬 수 있다.

gyeol-ui는 이 기능으로 두 단계를 만든다. 먼저 Primitive 표에 실제 값을 적는다. 그다음 Semantic 표의 칸은 값을 직접 적지 않고 Primitive나 다른 Semantic을 가리킨다.

Primitive 열 1개. 실제 값을 적는다
Variable modevalue
color/white #FFFFFF
color/gray/50 #FAFAFA
color/gray/200 #E4E4E7
color/gray/700 #3F3F46
color/gray/900 #18181B
color/blue/300 #8DB1F0
color/blue/500 #2F62B5
spacing/4 16
Semantic 열 = Color Scheme. Primitive나 다른 Semantic을 가리킨다
Variable modelight modedark
bg-surface color/gray/50 color/gray/900
fg-default color/gray/900 color/gray/50
bg-accent color/blue/500 color/blue/300
border-default color/gray/200 color/white · 10%
ring-offset bg-surface bg-surface

→ 표시가 있는 칸은 값이 아니라 가리키는 Variable의 이름이다. 색 견본은 가리킨 끝에서 찾은 값이다. 파랗게 칠한 칸은 아래에서 설명하는 두 가지 특별한 경우다. 값은 설명을 위한 예시다.

화면이 bg-surface를 dark 열로 그릴 때 값을 찾는 순서는 아래와 같다.

dark 화면 bg-surface화면이 쓴 이름 Semantic의 dark 열 color/gray/900가리키는 Variable Primitive의 값 #18181B실제 색

이렇게 나누면 역할이 갈린다. 회색 900을 조금 더 진하게 바꾸려면 Primitive 한 칸만 고치면 된다. 그러면 그 회색을 가리키는 모든 Semantic이 따라온다. 반대로 "어두운 화면의 바탕을 회색 800으로 바꾸자"는 결정은 Semantic 한 칸만 고친다.

같은 표 안을 가리키기

ring-offset은 Primitive가 아니라 같은 Semantic 표의 bg-surface를 가리킨다. 같은 collection 안을 가리키면 Figma는 지금 쓰는 열 그대로 찾는다. dark 열의 ring-offset은 dark 열의 bg-surface로 간다. 그래서 light와 dark가 섞일 일이 없고, 바탕색을 바꾸면 ring-offset도 따라온다.

가리키면서 투명도 걸기

Figma는 alias에 투명도를 따로 걸 수 있다. dark 열의 border-default는 "color/white를 불투명도 10%로"다. 어두운 바탕 위에 흰색을 살짝 얹으면 바탕보다 조금 밝은 선이 된다. Semantic의 alpha 그룹 (alpha/90 등)도 이 방식으로 바탕색에 투명도를 건 단계다.

DTCG 표준에는 "가리키면서 투명도만 바꾸기"를 적는 방법이 없다. 그래서 내보낼 때 계산한 색을 표준 값으로 적고, 무엇을 가리켰는지와 투명도는 확장 데이터에 따로 남긴다. CSS에서는 color-mix()로 연결을 되살린다. 코드로 옮기면에서 모양을 본다.

왜 표가 두 장인가

gyeol-ui에서 바뀌는 축은 Color Scheme(light/dark) 하나다. 그런데도 표를 두 장으로 나눈다. 한 장에 다 넣으면 어떻게 되는지 보면 이유가 보인다.

방법 1. 표 한 장에 다 넣기

한 장짜리 collection 열 = Color Scheme. 칸에 실제 값을 적는다
Variable modelight modedark
bg-surface #FAFAFA #18181B
fg-default #18181B #FAFAFA
bg-accent #2F62B5 #8DB1F0
spacing/4 16 16

주황 칸은 같은 값이 또 적힌 곳이다. 회색 900(#18181B)이 bg-surface의 dark와 fg-default의 light에 따로 적혀 있다. 회색 900을 바꾸려면 이 칸을 모두 찾아 고쳐야 한다. 실제 시스템에서는 수십 칸이다. 간격처럼 명암과 무관한 값도 두 번 적어야 한다.

방법 2. 표 두 장으로 나누기 (gyeol-ui의 선택)

Alias에서 본 구조다. 실제 값은 열이 하나인 Primitive 표에 한 번만 적고, Semantic 표는 그 이름을 가리킨다.

할 일 방법 1. 한 장 방법 2. 두 장
회색 900 바꾸기 그 색이 적힌 칸을 모두 찾아 고친다 Primitive 1칸
간격 넣기 light와 dark에 같은 값을 두 번 Primitive에 한 번
"어두운 바탕을 회색 800으로" 값을 찾아 고친다 Semantic 1칸의 가리키는 곳만 바꾼다

두 장으로 나누면 "무슨 색인가"(Primitive)와 "어디에 쓰나"(Semantic)가 다른 표에 한 번씩만 적힌다. 그래서 한쪽을 바꿔도 다른 쪽은 그대로다.

화면에 Mode 정하기

Figma에서 frame을 고르고 오른쪽 사이드바 Appearance의 "Apply variable mode"를 누르면 collection마다 어느 열을 쓸지 고른다. Mode는 collection마다 따로 고른다. gyeol-ui에서 고를 것이 있는 표는 Semantic 하나다. Primitive는 열이 하나뿐이다.

아무것도 고르지 않으면 Auto다. Auto인 레이어는 부모 frame의 Mode를 따른다. 부모도 Auto면 위로 계속 올라가고, 끝까지 정한 곳이 없으면 collection의 기본 Mode(맨 왼쪽 열)를 쓴다.

두 화면 모두 Primitive 표는 똑같다. Semantic 열만 바뀌어, 같은 이름이 다른 Primitive를 가리키게 된다.

코드로 옮기면

아래 내용은 토큰 파이프라인 스펙에서 정한 계획이고, 아직 구현하지 않았다. 핵심은 Figma의 표 그림이 그대로 파일과 CSS로 옮겨진다는 것이다.

Figma 토큰 JSON (DTCG) CSS
Variable bg-surface 토큰 bg-surface 변수 --gyeol-bg-surface
표의 열 하나 (Semantic의 dark) 파일 하나 semantic/dark.json 블록 하나 (dark일 때 적용되는 선택자)
alias (→ color/gray/900) "$value": "{color.gray.900}" var(--gyeol-color-gray-900)
alias + 투명도 (→ color/white · 10%) 계산한 색 + 확장 데이터 color-mix(…)
화면의 Mode 고르기 없음 data-color-scheme 속성이나 OS 설정

열 하나가 파일 하나

  • packages/tokens/tokens/
    • primitive.json Primitive 표 (열 1개)
    • semantic/ Semantic 표
      • light.json light 열
      • dark.json dark 열

Figma의 기본 DTCG 내보내기와 가져오기도 같은 단위(Mode 하나당 파일 하나)로 동작한다. Primitive 파일에는 실제 색을 적는다. color 그룹에 $type을 한 번 적으면 그 안의 모든 토큰이 색으로 취급된다. 

{
  "color": {
    "$type": "color",
    "gray": {
      "900": {
        "$value": {
          "colorSpace": "srgb",
          "components": [0.094, 0.094, 0.106],
          "hex": "#18181b"
        }
      }
    }
  }
}

Semantic의 dark 열 파일은 Primitive를 가리킨다. Semantic에는 color 그룹이 없어서, 아래 예시는 $type을 토큰마다 적었다. 파일 맨 위에 한 번만 적을 수 있는지는 스펙에서 확인한다. 

{
  "bg-surface": { "$type": "color", "$value": "{color.gray.900}" }
}

열 하나가 CSS 블록 하나

CSS에서는 "화면에 Mode를 정하는 것"이 선택자가 된다. Primitive는 열이 하나라 :root 한 곳에 낸다. Semantic 블록은 Color Scheme에 따라 적용되고, 값이 아니라 var()로 Primitive를 가리킨다. Figma의 alias와 똑같은 구조다. 투명도를 건 alias는 color-mix()가 된다. 아래는 계획한 출력 모양이다. 

/* Primitive 표 */
:root {
  --gyeol-color-white: #ffffff;
  --gyeol-color-gray-50: #fafafa;
  --gyeol-color-gray-200: #e4e4e7;
  --gyeol-color-gray-900: #18181b;
}

/* Semantic 표의 light 열 */
:root {
  color-scheme: light;
  --gyeol-bg-surface: var(--gyeol-color-gray-50);
  --gyeol-border-default: var(--gyeol-color-gray-200);
}

/* Semantic 표의 dark 열: OS가 어둡고 사용자가 light로 덮어쓰지 않았을 때 */
@media (prefers-color-scheme: dark) {
  :root:not([data-color-scheme="light"]) {
    color-scheme: dark;
    --gyeol-bg-surface: var(--gyeol-color-gray-900);
    --gyeol-border-default: color-mix(in srgb, var(--gyeol-color-white) 10%, transparent);
  }
}

/* Semantic 표의 dark 열: 속성으로 직접 골랐을 때 */
[data-color-scheme="dark"] {
  color-scheme: dark;
  --gyeol-bg-surface: var(--gyeol-color-gray-900);
  --gyeol-border-default: color-mix(in srgb, var(--gyeol-color-white) 10%, transparent);
}

이름이 바뀌는 과정

Primitive color/gray/900Figma / → . color.gray.900토큰 JSON CSS 이름 규칙 --gyeol-color-gray-900CSS 변수
Semantic alpha/90Figma / → . alpha.90토큰 JSON CSS 이름 규칙 --gyeol-alpha-90CSS 변수

경로 칸을 -로 이어 붙이므로 alpha.90과 alpha-90은 같은 CSS 변수가 된다. 그래서 모든 토큰의 CSS 변수 이름이 서로 다른지 빌드 때 검사한다.

용어 정리

Figma 용어와 gyeol-ui 용어(GLOSSARY.md)는 아래처럼 대응한다.

GLOSSARY의 Color Scheme 항목은 "Mode"라는 말을 피하라고 적어 두었다. Figma에서 Mode는 "표의 열" 일반을 뜻해서, light/dark를 "Mode"라고 부르면 Figma 개념과 헷갈리기 때문이다.

점검 문제

1. 회색 900을 조금 더 진하게 바꾸면 무엇을 고치나?

왜 표가 두 장인가와 코드로 옮기면의 그림으로 생각한다. Figma 표, 파일, CSS 각각에서 답한다.

답 보기

Figma에서는 Primitive 표의 color/gray/900 한 칸이다. 파일은 primitive.json의 한 줄, CSS는 :root의 --gyeol-color-gray-900 한 줄이 바뀐다. 그 회색을 가리키는 Semantic은 이름만 가리키므로 아무것도 고치지 않아도 새 값을 쓴다.

2. 경고 배경색 bg-danger를 더하면 어디를 고치나?

경고 배경은 밝은 화면과 어두운 화면에서 달라야 한다. Collection의 "같은 열" 규칙으로 생각한다.

답 보기

명암에 따라 바뀌므로 Semantic 표에 행 하나를 더한다. 표의 규칙 때문에 light 칸과 dark 칸이 함께 생기고, 각각에 가리킬 Primitive(예: 빨강 계열)를 적는다. 그 빨강이 Primitive에 없으면 Primitive 표에도 행을 더한다. 파일로는 semantic/light.json과 semantic/dark.json에 한 줄씩 들어간다. Semantic 칸에 색을 직접 적으면 빌드가 실패하도록 정했다.

3. 모서리 둥글기 radius/md는 어느 표에 넣나?

"무엇에 따라 바뀌는가"로 생각한다.

답 보기

Primitive 표다. 둥글기는 명암에 따라 바뀌지 않는다. Semantic 표에 넣으면 light와 dark에 같은 값을 두 번 적어야 한다. 간격을 Primitive에 둔 것과 같은 이유이고, 컴포넌트는 --gyeol-radius-md를 직접 쓴다.
